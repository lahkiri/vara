## 0. عن هذه الوثيقة

هذه الوثيقة هي الطبقة الثالثة والأخيرة في سلسلة تعريف Vara:

```text
الوثيقة 1 — الرؤية        : لماذا Vara موجود وما هو (المهمة، التمايز، الفلسفة)
الوثيقة 2 — الـ Stack      : بأي تقنية يُبنى (Rust, SQLite, Tauri, llama.cpp ...)
هذه الوثيقة — القرارات     : كيف يُبنى بشكل صحيح (الإصلاحات، الواجهات، الخطة، الحراسة)
```

دورها ليس تكرار ما قبلهها، بل:

1. **تثبيت** كل قرار معماري في وثيقة الـ Stack بصيغة ADR رسمية قابلة للفحص، حتى لا يُعاد فتح أي قرار خاطف أثناء التنفيذ.
2. **إغلاق** الثغرات التنفيذية التي كشفتها المراجعتان الهندسيتان — الثغرات التي تصف الرؤية والـ Stack "النية"، بينما هذه الوثيقة تعرف "السلوك عند الحافة".
3. **تجهيز البناء الفعلي**: Schema كامل جاهز للتنفيذ، هيكل مستودع جاهز للإنشاء، خطة MVP بمعايير قبول قابلة للقياس، سجل مخاطر حي، وقائمة استبعاد صريحة.

**قاعدة الاستخدام:** هذا الملف هو مرجع الحكم في أي خلاف تنفيذي. أي تعديل معماري مستقبلي يدخل كـ `ADR-023` وما بعده بنفس القالب — لا يُعدَّل قرار مقرَّر إلا بـ ADR بديلة تشير إليها صراحة.

## 0.1 قالب ADR المعتمد

كل قرار في هذه الوثيقة يتبع القالب التالي:

| الحقل | المعنى |
|---|---|
| **الحالة** | `مقرَّر` — قابل للتغيير فقط عبر ADR جديدة تشير إليه |
| **التصنيف** | `تثبيت` (قرارك الأصلي الذي نعتمده) / `إصلاح` (يغلق ثغرة كشفناها) / `سدّ` (يغلق نقصاً غير مذكور سابقاً) |
| **يغلق** | رقم الثغرة من خريطة إغلاق الثغرات (0.2) إن وُجدت |
| **السياق** | المشكلة الفعلية، متى تظهر، ولماذا هي خطيرة |
| **البدائل المدروسة** | كل بديل مع **سبب الرفض المحدد** — لا يُقبل "لم نحبه" |
| **القرار** | المواصفة الكاملة بما يكفي للتنفيذ دون تفسير حر |
| **العواقب** | الإيجابيات، والتكاليف/السلبيات المعترف بها صراحة |
| **قاعدة الفحص** | جملة واحدة قابلة للتحقق — تُستخدم في مراجعة الكود و CI |

> **لماذا "قاعدة الفحص"؟** لأن الفرق بين قرار معماري حقيقي وخطاب جميل هو: هل يمكن لآلة أو مراجع كود أن يقول "هذا يخالف القرار"؟ كل ADR هنا ينتهي بقاعدة قابلة للفحص آلياً أو يدوياً في دقيقة واحدة.
>
> **حالتان فقط لحالة القرار (مضافة v1.1):**
> - **مقرَّرة** — مبنية على دليل قابل للفحص (اختبار، مصفوفة، واقعة). إعادة فتحها تمر حصراً بـ ADR جديدة `supersedes`.
> - **مؤقتة** — فرضية معقولة تنتظر دليلاً؛ يجب أن تحمل **شرط تأكيد** وموعد فحص معلنين. المؤقتة لا "تتصلب" بالتكرار: بلوغ الموعد دون تحقق الشرط = فتح القرار وتغييره، لا تمديده افتراضياً. تثبيت قرار قبل وجود دليل = عبء إثبات مقلوب.

# الجزء الأول — القرارات المعمارية (ADRs)

## المجموعة أ — تثبيت قرارات الـ Stack

هذه الثمانية قرارات جاءت من وثيقة الـ Stack وتُثبَّت هنا بصيغة قابلة للفحص. اختصار السياق لأنها مناقشة سابقة — الثقل هنا في **قاعدة الفحص** التي تحميها من التآكل أثناء التنفيذ.

---

### ADR-001 — Rust هي لغة أساس Vara Core

**الحالة:** مؤقتة حتى نهاية المرحلة 1 · **التصنيف:** تثبيت · (محدّثة v1.1 — كانت "مقرَّرة" بينما R-01 مسجلة عالٍ/عالٍ؛ التناقض يُحسم بشرط تأكيد لا بتفاؤل)

**السياق:** Vara كيان دائم التشغيل: scheduling، process management، sandboxing، crash recovery، عشرات الـ actors المتزامنة، أعمار تشغيل تُقاس بالأسابيع. الذاكرة الآمنة بلا GC وسقوط بنية يعني أن الكيان لا "يتعب" مع الوقت.

**القرار:** Rust (edition 2021+) لكل الـ Core. Python/TS مسموحان **فقط داخل مهارات sidecar معزولة** — ليسا في مسار الـ runtime.

**العواقب:** إيجابية: أداء ثابت، crash domains صغيرة، بيئة crates ناضجة للعمل المطلوب. سلبية: سرعة تكرار أبطأ في منطق الوكلاء — يعالجها ADR-020 (Eval Harness) واعتماد المهارات على ملفات Markdown قابلة للتعديل بلا إعادة بناء.

**شرط التأكيد (نهاية المرحلة 1 — مُلزم):** يُقاس زمن الدورة الفعلي بين "فكرة تعديل في منطق الوكلاء (compiler/planning/تنظيم)" و"تجربة مقيسة على GM-1". إذا تجاوز الوسيط ساعتين بسبب البنية (مؤشر R-01 محقق) — تُفتح ADR-023 لطبقة scripting للمنطق التنظيمي (Rhai أو Lua) داخل الـ Core، ويبقى Rust للبنية التحتية. إذا لم يتحقق المؤشر — الحالة تصبح "مقرَّرة" نهائياً ويُحدَّث هذا السطر.

**قاعدة الفحص:** أي `*.py` أو `*.ts` في المستودع يعيش فقط تحت `skills-builtin/` أو داخل Skill Package — يفحصها CI script بسطر واحد. وفحص الحالة: بند "قياس زمن الدورة" إلزامي في DoD المرحلة 1 — لا إغلاق للمرحلة بلا رقمه.

### ADR-002 — Modular Monolith أولاً، لا Microservices

**الحالة:** مقرَّر · **التصنيف:** تثبيت

**السياق:** Vara يجب أن يبدأ بـ double-click على جهاز 8GB. كل service مقيمة = 50-150MB RAM + فشل توزيعي + تعقيد نشر يقتل الهدف. الاستثناء الوحيد المشروع: عزل العمليات الخطر (يغطيه ADR-015).

**القرار:** عملية واحدة `vara-core` بوحدات داخلية نظيفة (crates منفصلة بـ Rust workspace — انظر القسم 5). العمليات الثانوية تنشأ **فقط** كـ sandbox/browser/model workers عند الحاجة الفعلية، وتُقتل دائماً عند انتهاء مهمتها.

**العواقب:** إيجابية: RAM idle منخفضة، نشر = ملف واحد، تتبع أخطاء بسيط. سلبية: حدود الوحدات تُفرض بـ CI (قاعدة الفحص) لا بالعملية — انضباط إضافي مطلوب.

**قاعدة الفحص:** `cargo tree` + قواعد الاعتماديات في القسم 5.4 — أي crate ينتهك الطبقية يُرفض في CI.

### ADR-003 — Tokio كـ Async Runtime وحيد

**الحالة:** مقرَّر · **التصنيف:** تثبيت

**السياق:** في نفس اللحظة: وكيل ينتظر LLM، وكيل يقرأ ملفات، أداة تشغّل، جدولة تحدث، أحداث تُبث. الـ threads الخام أو الـ blocking I/O في هذا الوضع = إهدار موارد الجهاز الضعيف نفسه الذي يُبنى من أجله.

**القرار:** `tokio` multi-threaded runtime لكل الإنتاج. `tokio::sync::mpsc` **bounded** لكل صناديق البريد وقنوات الأحداث (سياسة الـ backpressure في ADR-010). يُمنع `std::thread::spawn` في مسار الطلبات؛ `spawn_blocking` مسموح فقط للـ I/O المتزامن الحتمي (hashing ملفات ضخمة، ضغط).

**العواقب:** إيجابية: آلاف الـ actors الخفيفة، ألغاء هيكلي عبر `CancellationToken`. سلبية: قيود Send/Sync تدخل في التصميم المبكر — أثمن من إعادة كتابة لاحقة.

**قاعدة الفحص:** Lint في CI يمنع `std::thread` و`async` بلا `tokio` خارج crates الـ sandbox.

### ADR-004 — Virtual Agents: الوكلاء Actors داخل عملية، لا Processes

**الحالة:** مقرَّر · **التصنيف:** تثبيت · **يتكامل مع:** ADR-010

**السياق:** Vara قد يصل لعشرات إلى مئات الوكلاء المنطقيين. process لكل وكيل = عشرات الميجابايتات لكل كيان وهمي، على الجهاز نفسه الذي يشغّل LLM. والعكس خاطئ أيضاً: وضع كل شيء كـ async task بلا حدود يخلط العزل المنطقي بالعزل العملي.

**القرار:** ثلاث طبقات تنفيذ واضحة:

```text
طبقة 1 — Actor (افتراضي):   Tokio task + mailbox في SQLite + حالة في ذاكرة
                            يدعم مئات الوكلاء بكلفة كيلوبايتات لكل وكيل
طبقة 2 — Worker Process:    لكل أداة تحتاج عزلاً خفيفاً (browser worker, untrusted script)
                            تُنشأ عند الطلب، عمرها = عمر المهمة
طبقة 3 — Sandboxed Process: للأكواد غير الموثوقة والمهارات عالية الخطورة (ADR-015)
```

الوكيل المنطقي يحمل: `identity, skills, memory_scope, mission, mailbox, state, budget, permissions, tools` — لكنه **ليس** عملية نظام أبداً.

**العواقب:** إيجابية: اقتصاد موارد يسمح بالكثافة التنظيمية التي تعد بها الرؤية. سلبية: يجب حماية الحالة المشتركة — يفرضها ADR-009 (كاتب وحيد) وADR-010 (صندوق بريد دائم).

**قاعدة الفحص:** لا `std::process::Command` في `vara-agents` ولا `vara-core` — تُفحص من CI؛ إنشاء العمليات مقصور على `vara-sandbox` و`vara-gateway` (llama-server) وحدهما.

### ADR-005 — SQLite + WAL هو متجر الحالة الوحيد

**الحالة:** مقرَّر · **التصنيف:** تثبيت

**السياق:** Vara desktop-first. PostgreSQL/Redis/Kafka تتطلب خدمات مقيمة تكسر قرار ADR-002 وهدف "double click". SQLite مع WAL يعطي قراءة متزامنة مع كاتب واحد — وهو تماماً نمط استخدام كيان محلي.

**القرار:** SQLite كمتجر وحيد للحالة والذاكرة (metadata) والأحداث والاقتصاد. الإعدادات الإلزامية عند فتح أي اتصال:

```sql
PRAGMA journal_mode = WAL;      -- قراء متوازون + كاتب واحد
PRAGMA synchronous = NORMAL;    -- توازن متانة/أداء مقبول مع WAL
PRAGMA foreign_keys = ON;       -- لا سلامة مرجعية بلا هذا
PRAGMA busy_timeout = 5000;     -- لا فشل فوري عند التنازع المؤقت
PRAGMA wal_autocheckpoint = 1000; -- منع تضخم ملف WAL
```

الملفات الكبيرة (artifacts) خارج الـ DB بنظام content-addressed — ADR-022.

**البدائل المدروسة:**

| البديل | سبب الرفض |
|---|---|
| PostgreSQL | يتطلب خدمة مقيمة + نشر معقد — يخالف ADR-002 |
| MongoDB | بلا معاملات صارمة في الحدود القديمة + خدمة مقيمة |
| sled/redb (embedded Rust) | نضج أقل بكثير، بلا FTS5 ولا امتداد vec، بلا أدوات فحص تُضاهي sqlite3 CLI |
| DuckDB | ممتاز للتحليل OLAP، خاطئ للحالة Transactional — مكانه لاحقاً كـ workspace تحليلي (قائمة الاستبعاد X-07) |

**العواقب:** إيجابية: نسخ احتياطي = نسخ ملف، أدوات نضج لا نهاية لها، export مباشر. سلبية: الكاتب الواحد — هذا بالضبط موضوع ADR-009.

**قاعدة الفحص:** لا اتصال SQLite في الكود بلا الـ PRAGMAs الخمسة أعلاه — تُفرض عبر دالة واحدة `open_db()` في `vara-state`، وأي `Connection::open` مباشرة في مكان آخر يُرفض بـ CI.

### ADR-006 — Tauri 2 + Svelte 5 للواجهة

**الحالة:** مؤقتة حتى أول شريحة UI عاملة في المرحلة 3 · **التصنيف:** تثبيت · (محدّثة v1.1 — فرضية لم تُختبر بعد لا قرار مثبت)

**السياق:** Vara نفسه يحمل LLM وذاكرة على جهاز ضعيف — شحن Chromium كامل (Electron) لعرض شجرة تنظيم وأحداث حية هدر مزدوج. ولا يوجد مبرر لـ Next.js: بلا SSR، بلا server components، بلا routes سحابية.

**القرار:** Tauri 2 (WebView النظام + backend Rust) وSvelte 5 (runes) للواجهة. الـ UI تفاعلاتها كلها عبر Tauri IPC / WebSocket — ومبدأها الملزم هو ADR-021: الواجهة projection للحدث، لا صاحبة حالة.

**العواقب:** إيجابية: حجم تطبيق صغير، استهلاك idle شبه صفري، الواجهة قابلة للاستبدال كلياً دون لمس الـ Core. سلبية: تقلب WebKitGTK على Linux — مخاطرة R-08 مع خطة تخفيف.

**شرط التأكيد (أول شريحة UI عاملة):** بث events من الـ Core إلى شجرة تنظيم حية عبر Tauri IPC. إن ثبت أن جسور IPC/event والتغليف تستهلك وقتاً غير متناسب مع القيمة (مؤشر: > أسبوع عمل على الشريحة الأولى بلا سبب نطاقي) — تُفتح ADR لدراسة البديل "web app محلي يفتح في المتصفح" بدل Tauri، بلا تعصب للقرار المكتوب.

**قاعدة الفحص:** لا crate في الـ workspace يعتمد على `tauri` إلا `app/src-tauri` — فحص `cargo tree` في CI.

### ADR-007 — Model Gateway + llama.cpp كـ Sidecar Process

**الحالة:** مقرَّر · **التصنيف:** تثبيت · **يتطور إلى:** ADR-014

**السياق:** ربط الـ Core مباشرة بمحرك استدلال واحد = كيان مشدود بمزود واحد، يخالف مبدأ "الذكاء قابل للاستبدال، الكيان لا". وتضمين محرك الاستدلال داخل عملية Vara = انهيار الواجهة إذا انهار النموذج.

**القرار:** طبقة `Model Gateway` هي **المدخل الوحيد** للذكاء في Vara — لا استدعاء LLM خارجها إطلاقاً (قاعدة لا تُكسر رقم 3). الاستدلال المحلي عبر `llama-server` كعملية sidecar مستقلة يتحدث OpenAI-compatible API. موت llama-server = حدث يُبث ويُعالج، لا سقوط للكيان. تفاصيل التجويد والاقتصاد في ADR-014.

**العواقب:** إيجابية: استبدال المحرك/المزود بلا لمس الـ Core، عزل الأعطال، قياس مركزي للتكلفة. سلبية: hop إضافي (نسبته من الثواني لا تُقاس أمام زمن الاستدلال نفسه).

**قاعدة الفحص:** `grep` في CI: لا `reqwest`/`http client` لاستدعاء نموذج خارج `vara-gateway`.

### ADR-008 — Event-Driven Wakeups: لا لوب تفكير دائم

**الحالة:** مقرَّر · **التصنيف:** تثبيت

**السياق:** الكيان الذي "يسأل نفسه كل ثانية ماذا أفعل؟" يحرق battery وtokens وأرقام فواتير الاستدلال — ويخالف مباشرة فلسفة "أهم optimization". الاستيقاظ يجب أن يكون سببه شيء، لا تردد مؤقت أعمى.

**القرار:** الوكلاء لا يستهلكون CPU ولا tokens إلا عند حدث واقعي:

```text
مصادر الإيقاظ الشرعية:
file_changed | timer_fired (مجدول، لا متكرر) | agent_message_received
tool_completed | tool_failed | deadline_reached | budget_warning
mission_assigned | human_note | checkpoint_restored
```

كل استيقاظ يمر من بوابة حتمية: `is_reasoning_needed?(event)` — تصنيف L0 (كود، بلا نموذج). الأحداث التي لا تستدعي استدلالاً تُخزن وتُستأنف لاحقاً أو تُهمل حسب النوع، بلا استدعاء نموذج واحد.

**العواقب:** إيجابية: RAM idle ~ صفر CPU، فاتورة استدلال تتناسب مع العمل الفعلي لا مع زمن التشغيل. سلبية: الخطأ في تصنيف "لا يحتاج استدلالاً" يؤخر رد فعل — يعالجها حدث `budget_warning` وتظل الجدولة من أولويات المصادر الشرعية.

**قاعدة الفحص:** لا `tokio::time::interval` يحتوي استدعاء ModelProvider داخل جسمه — فحص يدوي مدرج في checklist مراجعة الكود + اختبار وحدة يثبت أن 60 ثانية idle بلا أحداث = صفر استدعاءات نموذج.

### ADR-009 — Persistence Actor: كاتب وحيد لـ SQLite

**الحالة:** مقرَّر · **التصنيف:** إصلاح · **يغلق:** G-01

**السياق:** WAL يمنح قرّاء متوازين، لكن الكاتب واحد في كل لحظة. وثيقة الـ Stack تتوقع عشرات الـ actors يكتبون أحداثاً وذكريات وحالات tool calls بشكل متزامن. بدون تصميم صريح، كل وكيل يكتب مباشرة = تنافس على قفل الكتابة → `SQLITE_BUSY` المتكرر، تراكم `busy_timeout`، وتدهور كشف بعد الوصول لعدد معين من الوكلاء — أي في منتصف المرحلة 2، حيث تصحيحه مكلف.

**البدائل المدروسة:**

| البديل | سبب الرفض |
|---|---|
| كل وكيل يفتح اتصاله ويكتب مباشرة | تنافس حتمي على قفل الكتابة؛ ينهار بالضبط عند كثرة الوكلاء — الحالة التي صمم Vara من أجلها |
| رفع `busy_timeout` والصبر | يخفي المشكلة ولا يحلها؛ زمن استجابة يتذبذب مع الحمل، والأولوية بين الكتّاب عشوائية |
| SQLightning/multiple connections مع `wal2` | غير ناضج، ومشكلة الأولوية والدفعات تبقى بلا حل |
| قاعدة بيانات مع كتّاب متعددين (Postgres) | يخالف ADR-002 وADR-005 |

**القرار:** نمط معماري كامل، لا تفصيلة:

```text
كل الوحدات (agents, scheduler, tools, UI)
      │  فقط عبر قنوات رسائل — لا SQL
      ▼
Persistence Actor  (tokio task وحيد يملك اتصال الكتابة)
      │  1) يستقبل طلبات الكتابة من mbox داخلي bounded
      │  2) يجمعها دفعات: flush عند (N=64 عملية) أو (25ms، أيهما أسبق)
      │  3) يكتب كل دفعة في معاملة واحدة قصيرة
      │  4) يرجع الإيصالات (ids) للطالبين عبر oneshot channels
      │  5) الأولوية: events/ledger > mailbox > state updates > analytics
      ▼
SQLite (WAL)
```

قواعد ملزمة مصاحبة: (أ) كل الكتابات عبر الـ Actor — القراء يفتحون اتصالات read-only بحرية، (ب) لا معاملة تتجاوز 50ms ظاهرياً — يُقاس في الاختبارات، (ج) عند امتلاء قناة الطلبات يُبث `persistence_backpressure` ويُبطئ المرسلون، لا يُفقد شيء، (د) كل طلب كتابة حرج (mailbox, checkpoint) ينتظر الإيصال؛ غير الحرج (analytics) fire-and-forget مع إمكانية الفحص.

**العواقب:** إيجابية: صفر `SQLITE_BUSY` في المسار الطبيعي، ترتيب حتمي للكتابة، نقطة واحدة لقياس I/O. سلبية: نقطة مركزية — يخففها أن الـ Actor بلا منطق أعمال (نقل بيانات فقط) وأن فشله قابل للاستعادة (يُعاد بناؤه من رسائله غير المسلّمة).

**قاعدة الفحص:** CI test: 50 actor يكتبون 1000 حدث لكل واحد بالتوازي → صفر أخطاء busy، وكل حدث موجود مرة بالترتيب. وأي `Connection` كتابة خارج `vara-state::persistence` يُرفض بـ CI.

### ADR-010 — بروتوكول حياة الـ Actor: Mailbox دائم + Supervision + إلغاء نظيف

**الحالة:** مقرَّر · **التصنيف:** إصلاح · **يغلق:** G-02 و G-03

**السياق:** وثيقة الـ Stack صحيحة في "Actor بحدث وحالة" — لكن السيناريو السهل 20% من العمل. الـ 80% هي الحواف: وكيل معلّق بانتظار رد يُقتل معه بريده إن كان في الذاكرة؛ مهمة تُلغى وأداة متصفح في منتصفها تترك عملية يتيمة وملفات مؤقتة؛ وكيل يفشل 3 مرات فمن يقرر مصيره؟ هذه الحالات هي التي تفصل demo عن كيان دائم.

**البدائل المدروسة:**

| البديل | سبب الرفض |
|---|---|
| Mailbox في الذاكرة (tokio mpsc فقط) | انهيار = فقدان رسائل لم تُعالج؛ يخالف جوهر "كيان لا ينسى" |
| كل وكيل process معزولة + supervisor خارجي | يكسر ADR-004 ويقتل كثافة الوكلاء على الأجهزة الضعيفة |
| إلغاء بالـ drop وحده | لا تنظيف: العمليات يتيمة، الملفات تبقى، الأقفال تُحجز |
| إعادة تشغيل الوكيل الفاشل بلا سقف | لوب فشل لا نهائي يحرق موارد بلا قرار |

**القرار:** ثلاثة بروتوكولات ملزمة لكل actor في Vara:

**1. Mailbox الدائم (durable-first):** كل رسالة تُكتب في `agent_mailbox` (SQLite) **قبل** تسليمها للـ actor الحي. الـ mpsc في الذاكرة مجرد "مؤشر تشغيل" فوق الجدول، والـ actor يرسم الرسائل بترتيب `seq`. وكيل suspended = لا task حي، ورسائله تتراكم في الجدول بأمان. الاستئناف = إنشاء task يقرأ من آخر `delivered_seq`. **لا رسالة تعيش في الذاكرة وحدها أبداً.**

**2. شجرة إشراف (Supervision):** كل وكيل له مشرف واحد محدد (Vara نفسه، أو manager agent). سياسة إعادة التشغيل صريحة وقابلة للتهيئة: `max_restarts = 3` خلال `5 دقائق`. عند تجاوزها يصدر قرار إشرافي من ثلاثة فقط: `escalate_to_human` (افتراضي) / `downgrade_role` (تكليف أصغر) / `terminate_preserve_knowledge` (أرشفة ذكرياته وإنهاؤه). أي قرار إشرافي = صف في `org_changes` + بث `AgentFailed/AgentRestarted` — لا إعادة تشغيل صامتة.

**3. الإلغاء النظيف (Cancellation Protocol):** كل عمل له `CancellationToken`، وكل أداة تُلزم بعقد إلغاء ثلاثي:

```rust
// عقد الأداة الملزم — أي أداة لا تلتزم به لا تُسجَّل في Registry
async fn execute(&self, ctx: ToolCtx) -> ToolResult;
// ToolCtx يفرض:
//   1. ctx.cancelled() يجب فحصها عند كل نقطة طويلة (قبل/بعد كل I/O كبير)
//   2. ctx.on_abort(|| cleanup()) — مسجلة قبل بدء العمل الفعلي
//   3. النتيجة إما ToolOutput أو ToolAborted{cleanuped: bool}
```

عند الإلغاء: يُبث `ToolCancelled` → `on_abort` ينظف (يقتل العملية اليتيمة، يحذف الملفات المؤقتة، يغلق الاتصالات) → تُحدَّث حالة المهمة بـ checkpoint → الحدث يُسجل في `audit_log`. الأدوات الغير idempotent (نشر، دفع) تُصنف `irreversible` في الـ Registry وتشترط `ask` من السياسة قبل التنفيذ (ADR for policies in `policies` table).

**العواقب:** إيجابية: لا رسالة ضائعة، لا عملية يتيمة، فشل متدرج بقرار موثق، استئناف مضمون. سلبية: كتابة أداة تتطلب انضباط العقد — يعوضه أن العقد يُفرض في التسجيل (`ToolRegistry` يرفض أداة بلا `on_abort` مُسجلة).

**قاعدة الفحص:** اختبارات القبول A1-T2 (قتل قسري أثناء انتظار رسالة → لا فقدان) و A1-T3 (إلغاء أثناء tool call → صفر عمليات يتيمة عبر فحص جدول العمليات بعد 5 ثوانٍ). وأي `mpsc` جديد لرسائل وكلاء يُرفض في مراجعة الكود إن لم يكن فوق `agent_mailbox`.

### ADR-011 — سياسة Event Sourcing والـ Checkpoints: حدث + لقطة، لا كليهما منفصلين

**الحالة:** مقرَّر · **التصنيف:** إصلاح · **يغلق:** G-04

**السياق:** "المنظمة كلها state machine قابلة للاستعادة" صحيحة كهدف، لكنه غامض تنفيذياً. تطرفان أخطأ كلاهما: (أ) حفظ كل شيء كـ events وإعادة تشغيلها عند الإقلاع → إقلاع يتضخم مع عمر الكيان، (ب) snapshots فقط → فقدان سبب كل حالة، و"اسأل لماذا اتخذ هذا القرار" يصبح مستحيلاً — وهذه القدرة مذكورة صراحة في وثيقة الرؤية.

**البدائل المدروسة:**

| البديل | سبب الرفض |
|---|---|
| Pure event sourcing (replay كامل عند الإقلاع) | إقلاع يتناسب طولاً مع عمر الكيان لا مع آخر حالته |
| Full snapshots فقط | لا تفسير قراري؛ تخزين متضخم لكل snapshot كامل |
| Snapshot كل N ثانية | snapshots بلا معنى دلالي؛ I/O مهدور (نفس خطأ "snapshot بعد كل token" المحسوم) |

**القرار:** **Hybrid دلالي — events دائماً + snapshots عند حدود دلالية:**

```text
كل شيء يُبث أولاً كـ event في جدول events (append-only، trigger يمنع UPDATE/DELETE)
الـ snapshots الحية (state الحالي في الجداول العادية) هي الحقيقة التشغيلية
checkpoints تُلتقط حصراً عند حدود دلالية:
   mission_state_transition | tool_completion | major_agent_decision
   organization_change | skill_promotion | manual | graceful_shutdown
الاستعادة (resume):
   1) الحية أصلاً في الجداول (SQLite استعادها) — لا يُعاد بناء شيء
   2) checkpoint يثبت نقطة الاتساق: مسبباته events <= seq محفوظ في صف الـ checkpoint
   3) ما بعد آخر checkpoint يُقرأ من events للفحص/التدقيق فقط — لا replay تنفيذي
```

المعنى العملي: الإقلاع زمنه ثابت مهما اشتعل الكيان، والاستفسار "لماذا فعلت هذا؟" يُجاب من `events` + `checkpoints` معاً، وأي فساد في الحالة الحية يُكشف بمقارنتها بأحدث checkpoint.

**العواقب:** إيجابية: إقلاع سريع دائم، تفسير كامل، تدقيق قابل للتنفيذ. سلبية: الجداول الحية والـ events يجب ألا يختلفا — يعالجه أن الحياة تُكتب عبر ADR-009 (كاتب وحيد، نفس المعاملة) والـ event يُكتب **في نفس معاملة** تغيير الحالة حين يكون مرتبطين.

**قاعدة الفحص:** اختبار A1-T2 (kill -9 → resume → الحتة بعد الـ checkpoint تُستأنف بلا تنفيذ مكرر لأداة غير idempotent) + trigger الـ append-only يُختبر أنه يرفض UPDATE فعلياً في CI.

### ADR-012 — قيود طبقات الذكاء: L1 بلا أدوات + Structured Output إجباري + ToolCallValidator

**الحالة:** مقرَّر · **التصنيف:** إصلاح · **يغلق:** G-05

**السياق:** وثيقة الـ Stack تعتمد على L1 (tiny model) في routing/classification/summarization. ما لم يُذكر: نماذج 1-3B **غير موثوقة إطلاقاً في function calling** — تخترع أسماء أدوات، تنسكب معاملاتها، أو تُخرج JSON مكسوراً. بناء L1 بأدوات = بناء فشل منهجي في أول جهاز ضعيف 8GB، حيث L1 هو الأكثر استخداماً.

**البدائل المدروسة:**

| البديل | سبب الرفض |
|---|---|
| L1 مع أدوات + صلاحية إعادة محاولة | إعادة المحاولة على نموذج ضعيف = هدر مع تكرار نفس الفشل |
| رفع L1 إلى نموذج 7B | يقتل الهدف (8GB لا تستوعب 7B + L2 + embeddings مريحين) |
| حظر L1 كلياً والاعتماد على L2 لكل شيء | يهدر أثمن مورد: استدلال عام في قرارات كان يكفي لها L0/L1 |
| Function calling بالاعتماد على أدب النموذج | موثوقية غير مضمونة أصلاً حتى في نماذج أكبر على مزودات متفرقة |

**القرار:** إعادة تعريف الطبقات بحدود صارمة تُفرض في الـ Gateway نفسه، لا في "نصائح للوكلاء":

```text
L0 deterministic  : كود فقط، بلا نموذج — تصنيف الأحداث، توجيه، قيود
L1 tiny (1-3B)    : مخرجات ذات بنية فقط — {classification, route, summary, score}
                    ✗ صفر أدوات ✗ صفر free-form generation صادرة كأمر
L2 general (7B+ محلي أو سحابي) : الوحيدة المخولة بـ tool calling
L3 heavy          : reasoning عميق + planning متعدد الخطوات
```

ثلاث آليات إجبار:

1. **GBNF/JSON Schema إلزامي:** كل استدعاء `structured()` في الـ Gateway يُلزِم النموذج محلياً بـ grammar (llama.cpp) أو response_format (سحابي). الطلب بلا schema يُرفض عند التصميم (نوع Rust يمنعه).
2. **ToolCallValidator قبل التنفيذ:** كل مخرجات tool call تمر حتماً عبر تحقق: الاسم موجود في Registry للوكيل المعني + كل المعاملات مطابقة للـ schema + الأداة مسموح بها في `policies` + الميزانية تستطيع. أي فشل = `ToolCallRejected` event + إعادة للنموذج مرة واحدة كحد أقصى، ثم `escalate`.
3. **فرض الطبقة في التوجيه:** `routing` في الـ Gateway يمنع بنائياً وصول `tools` مع طلب L1 — يُرمى الحقل مع `L1ToolsForbidden` event في الـ ledger.

**العواقب:** إيجابية: موثوقية L1 تصبح قابلة للضمان بدل الأمل، ووضوح حدود كل طبقة يجعل قياس جودتها ممكناً (ADR-020). سلبية: بعض القرارات تحتاج صعوداً لـ L2 حتى لو بدت صغيرة — مقبول، لأن الفشل الصامت أغلى من استدعاء إضافي.

**قاعدة الفحص:** اختبار A0-T3: حقن tool call من L1 → يجب رفضه حتماً. وأي `structured()` بلا schema لا يُترجم أصلاً (نظام الأنواع يمنعه).

### ADR-013 — استراتيجية الاسترجاع: RRF أولاً، Embeddings خاملة مجمعة، Rerank مؤجل

**الحالة:** مؤقتة حتى A2-T3 · **التصنيف:** إصلاح · **يغلق:** G-06 · (محدّثة v1.1 — آلية RRF ناضجة، لكن الأوزان وk=60 وsqlite-vec فرضيات تنتظر بيانات)

**السياق:** وثيقة الـ Stack حددت صيغة استرجاع غنية (semantic + lexical + importance + recency + ...) — لكنها لم تحدد **من يحسب الدمج وبأي كلفة**. Cross-encoder reranking على CPU جهاز ضعيف = ثوانٍ إضافية لكل بحث ذاكرة، وكل بحث ذاكرة يسبقه استدعاء reasoning. والنقطة الأعمى الثانية: الـ embeddings نفسها تحتاج نموذج embedding مقيم في RAM بجانب النموذج الرئيسي — على 8GB هذا خصم غير محسوب.

**البدائل المدروسة:**

| البديل | سبب الرفض |
|---|---|
| Cross-encoder rerank من اليوم الأول | زمن بحث يتضاعف على CPU؛ فائدة غير مثبتة قبل اختبار قاعدة بيانات حقيقية |
| embeddings متزامنة عند كل كتابة ذاكرة | تضخيم كل كتابة بكلفة نموذج؛ يكسر رشاقة الكتابة عبر ADR-009 |
| حذف Vector Search واكتفاء FTS5 | يخسر البحث الدلالي — جوهر "الذاكرة تفهم المعنى" في وثيقة الرؤية |
| خدمة rerank مستقلة | يخالف ADR-002 |

**القرار:** ثلاث مراحل ملزمة داخل `vara-memory`:

**1. الدمج بلا نموذج (RRF):** نتائج FTS5 + sqlite-vec + فلاتر metadata تُدمج بـ Reciprocal Rank Fusion بأوزان قابلة للتهيئة:

```text
score(d) = w_lex · 1/(k + rank_lex(d)) + w_sem · 1/(k + rank_sem(d))
         + w_meta · 1/(k + rank_meta(d))          // k = 60 افتراضياً
الأوزان الابتدائية: w_lex=0.4, w_sem=0.4, w_meta=0.2 — تُعاير من eval فقط، لا بذوق
```

**2. Embeddings خاملة مجمعة (lazy-batched):** لا embedding عند الكتابة. طابور `embedding_queue` يعمل: عند idle + دفعة ≥ 32 ذكرى + throttle (≥ 2s بين الدفعات). الذكريات غير المجهزة تُسترجع بالكلمات المفتاحية وحدها حتى تجهز — **لا فقدان وظيفي، فقط تغاير جودة مؤقت**، ويُبث `embedding_lag` إذا تجاوز الطابور 5000 ذكرى.

**3. Rerank مؤجل بشرط إعادة فتح:** cross-encoder ممنوع في v1. يُفتح فقط إذا: أثبت eval قياسي (ADR-020) أن RRF يفشل عتبة دقة معلنة على بيانات حقيقية، **و**زمن rerank المضاف ≤ 300ms p95 على جهاز مرجعي 8GB. بدون الشرطين معاً — لا.

**العواقب:** إيجابية: بحث ذاكرة بلا أي نموذج في المسار الساخن، ميزانية RAM واضحة (L2 + embedding صغير فقط)، قابلية قياس لكل تحسين لاحق. سلبية: دقة أولية أقل من نظام rerank كامل — مقصود: نقطة انطلاق قابلة للقياس أفضل من تعقيد غير مقيس.

**شرط التأكيد (A2-T3 + أسبوعا استخدام فعلياً):** الأوزان الابتدائية (0.4/0.4/0.2) وk=60 تُعايَر من eval استرجاع حقيقي لا من الذوق — إن أثبتت A2-T3 تفوق RRF بفارق موثق على العتبة المعلنة، تصبح الحالة "مقرَّرة". إن فشلت — تُفعَّل خطة X-10 (Qdrant Edge خلف نفس الـ trait) بلا مقاومة، لأن القرار كان مؤقتاً بالتعريف.

**قاعدة الفحص:** اختبار A2-T3: eval استرجاع على مجموعة ذكريات مثبتة — RRF يجب أن يتفوق على lexical فقط بفارق موثق، وزمن p95 للبحث ≤ 150ms على 100 ألف ذكرى. وأي استدعاء نموذج في مسار الاسترجاع يُرفض بـ CI (مع استثناء معطل صراحة للاختبار).

### ADR-014 — Model Gateway موحد: OpenAI-Compatible واحد + Budget Middleware + Cost Ledger

**الحالة:** مقرَّر · **التصنيف:** إصلاح · **يغلق:** G-07 · **يطور:** ADR-007

**السياق:** قائمة الـ providers في وثيقة الـ Stack (llama.cpp, Ollama, OpenAI, Anthropic, Google, Custom) = 6 adapters تُبنى وتُصان و تُختبر. في الحقيقة الهندسية: llama.cpp server وOllama وLM Studio وvLLM وOpenAI كلهم يتكلمون **نفس البروتوكول** (OpenAI-compatible API). بناء adapter لكل واحد = 70% عمل مكرر. والنقطة الأكبر: "الاقتصاد الداخلي" في وثيقة الرؤية يظل فلسفة ما لم يوجد مكان واحد تُحسب فيه كل token — وهو بالتعريف الـ Gateway.

**البدائل المدروسة:**

| البديل | سبب الرفض |
|---|---|
| adapter native لكل مزود من اليوم الأول | معظمهم OpenAI-compatible أصلاً؛ الجهد يُصرف على تكرار لا قيمة له |
| تمرير مفتاح API لكل وحدة تحتاجه | لا مركزية للقياس ولا فرض للميزانية؛ الأسرار متناثرة |
| الاقتصاد كجدول يُحدَّث من مواضع متفرقة | بلا نقطة اختناق = بلا فرض؛ الحساب يتفاوت ويُنسى |

**القرار:** ثلاثة مكوّنات داخل `vara-gateway`:

**1. ملف providers صغير وواقعي:**

```text
ModelProvider trait (الواجهة الوحيدة)
├── OpenAICompatibleProvider  ← يغطي فعلياً: llama.cpp, Ollama, LM Studio,
│                                vLLM, OpenAI, ومضيف المزودين المتوافقين
└── AnthropicProvider         ← native، فقط إن احتجنا قدراتهم الخاصة
(Purpose-based routing: كل نافذة تُطلب بغرضها l1/l2/l3/embedding — لا باسم نموذج)
```

إضافة مزود جديد = قرار ADR بحد ذاته، والافتراض: يظهر كـ OpenAI-compatible endpoint أولاً.

**2. Budget Middleware (حيث يصبح الاقتصاد كوداً):** كل استدعاء يمر حتماً عبر: `check_budget(scope) → reserve_estimate → call → settle_actual`. عند استنفاد ميزانية المهمة/الوكيل: الطلب يُرفض بـ `BudgetExhausted` event — والمهمة تتوقف بقرار موثق، لا تنضرب بصمت. الحجز يمنع السباق: 5 وكلاء متوازين لا يستطيعون معاً تجاوز ميزانية واحدة.

**3. Cost Ledger (append-only):** صف لكل استدعاء: من، لماذا (mission/agent/tool)، أي طبقة، tokens (input/output)، تكلفة تقديرية، زمن. هذا الجدول هو أساس: تقارير "كم كلفت المهمة" في الواجهة، وتعلم الكفاءة التنظيمية في الرؤية، وقرارات "هل أنشئ وكيلاً آخر؟".

**العواقب:** إيجابية: adapter واحد يخدم السوق الأكبر، فرض اقتصادي حقيقي لا معلن، قياس مركزي. سلبية: المزودون غير المتوافقين (بعض الأنطولوجات الخاصة) يحتاجون native adapter لاحقاً — قرار موجه لكل واحد على حدة.

**قاعدة الفحص:** اختبار A0-T1: أي استدعاء نموذج بلا صف ledger لاحق = فشل اختبار. وأي طلب يتجاوز ميزانية محجوزة = رفض حتمي (اختبار سباق: 5 tasks متوازية على ميزانية 3).

### ADR-015 — Sandbox تدريجي: Subprocess أولاً، WASM لاحقاً بشرط

**الحالة:** مقرَّر · **التصنيف:** إصلاح · **يغلق:** G-08

**السياق:** وثيقة الـ Stack ذكرت WASM/WASI كطبقة عزل محتملة — القرار سليم كرؤية، خاطئ كالتزام مبكر: WASI preview في تحرك مستمر، والوصول للـ filesystem/الشبكة فيه خشن. الالتزام بـ WASM كأساس عزل في v1 = مقامرة على أساس متغير تحت المبنى. والمقابل الصامت أخطر: تأجيل sandbox كله "حتى يستقر WASM" = تشغيل مهارات ذاتية الإنشاء بلا عزل — خط أحمر أمني.

**البدائل المدروسة:**

| البديل | سبب الرفض |
|---|---|
| WASM/WASI أساس العزل في v1 | أساس متحرك؛ قيود I/O غير مكتملة؛ بلا فائدة قبل وجود مهارات حسابية كثيرة |
| Docker كأساس العزل | يخالف قرار "لا Docker شرط للتشغيل" الصريح |
| Trust كامل للمهارات المروجة (بلا عزل لاحق) | promotion يثبت الجودة لا السلامة؛ skill موثوقة يمكن أن تُخترق (prompt injection) |
| العزل بالـ OS فقط بلا طبقات | كافٍ لـ v1 لكنه يغلق مستقبلاً عزل مهارات حسابية بحجم كلفة process كاملة |

**القرار:** سلّم عزل ثلاثي، كل درجة لها شرط صعود صريح:

```text
درجة 0 — In-process (trusted): أدوات مدمجة موقعة مع الإصدار، permissions من policies
درجة 1 — Subprocess (الافتراضي لـ v1):
   • بلا شبكة افتراضياً  • مجلدات workdir محددة  • timeout إجباري
   • سقف ذاكرة/وقت CPU   • خروج غير صفري = ToolFailed مع stderr محفوظ
   • Hardening حسب OS عند توفره: Linux (namespaces/seccomp/cgroups)
     Windows (Job Objects/restricted token — حدود موارد وقتل شجرة عمليات فقط؛
       حجب الشبكة **غير مضمون** بهذين وحدهما — انظر مصفوفة الضمانات أدناه)
     macOS (بديل عملي محدود — يوثق كقيد)
درجة 2 — WASM/WASI (مؤجل): للمهارات الحسابية البحتة فقط،
   يُفتح بعد استقرار WASI 0.3 + وجود ≥ 10 مهارات مرشحة فعلية (شرط إعادة فتح X-02)
```

قاعدة التوزيع: كل Skill تعلن `risk_level` في manifest، والـ Policy Engine يفرض: `low → in-process مسموح`، `medium → subprocess`، `high/critical → subprocess hardening + ask من المستخدم عند أول تشغيل`. **لا مهارة self-created تنزل تحت درجة 1 قبل 3 اختبارات ناجحة موثقة** (روابطها في ADR for skills pipeline، القسم 7).

**مصفوفة الضمانات لكل نظام (مضافة v1.1 — صادقة لا تسويقية):** وعد "بلا شبكة" يعني حجباً مضموناً تقنياً، لا نيّة. الحقيقة حسب OS:

| OS | حدود موارد | قتل شجرة العمليات | حجب شبكة مضمون | عواقب التصميم |
|---|---|---|---|---|
| Linux | cgroups | نعم (namespaces) | **نعم** (netns/seccomp) | A3-T1 بوابة إلزامية هنا |
| macOS | وسيط sandbox-exec | نعم | جزئي — يوثق كقيد | مهارات شبكية تحتاج موافقة صريحة |
| Windows | Job Objects | نعم | **لا في v1** (يتطلب AppContainer/قواعد firewall خارج النطاق) | مهارة self-created تحتاج شبكة = **رفض بنيوي** (declarative فقط) |

القاعدة المترتبة: على Windows v1، أي Skill منشأة ذاتياً تعلن حاجة شبكة في manifest تُرفض في خط الإنتاج قبل التشغيل — لا "محاولة وثقة". ضمان العزل الأقصى يبقى Linux.

**العواقب:** إيجابية: عزل حقيقي من أول يوم بأدوات ناضجة، مسار ترقية واضح لـ WASM بلا إعادة تصميم. سلبية: كلفة process لكل مهارة متوسطة الخطورة (~30-80MB لحظية) — مقبولة لأنها مصاحبة لعمل فعال ومحدودة العمر.

**قاعدة الفحص:** اختبار A3-T1 — **بوابة إلزامية على Linux فقط**: skill منشأة ذاتياً تحاول فتح socket شبكة → تفشل داخل sandbox بـ `SandboxViolation` وتُمنع من promotion. على Windows/macOS: نفس الاختبار يُشغَّل ويُوثَّق كقيد معلن (مصفوفة الضمانات أعلاه)، والحماية الفعلية هناك = رفض بنيوي لمهارات شبكية self-created + موافقة صريحة. وأي `Command::new` خارج `vara-sandbox` يُرفض بـ CI (قاعدة ADR-004).

### ADR-016 — الأسرار: OS Keychain + Fallback مشفر لوضع السيرفر

**الحالة:** مقرَّر · **التصنيف:** إصلاح · **يغلق:** G-09

**السياق:** قرار "OS keychain للـ API keys" صحيح على desktop (Windows Credential Manager / macOS Keychain / Linux Secret Service). لكن الثغرة: **خادم Linux headless لا يوجد فيه Secret Service أصلاً** — daemon mode (وهو جوهر قابلية النقل في الرؤية) ينكسر عند أول محاولة تخزين مفتاح. ومن دون حل صريح، يظهر الشيطان المألوف: مفاتيح plain-text في `state.db` لأن "الحل البديل المؤقت" يعيش للأبد.

**البدائل المدروسة:**

| البديل | سبب الرفض |
|---|---|
| ملف plain-text + chmod 600 | الملفات تُنسخ مع الـ export/backup؛ خط أحمر |
| متغيرات بيئة فقط | تسرّب عبر `/proc/<pid>/environ`، logs، وcrash dumps؛ صعب التدوير |
| تشفير يدوي بمفتاح في نفس المجلد | مسألة تخفي: مفتاح بجانب المُشفَّر = لا تشفير |
| Vault/خدمة خارجية | يخالف ADR-002 وروح local-first |

**القرار:** واجهة `SecretStore` واحدة، خلفها استراتيجية حسب البيئة:

```text
desktop (يوجد keychain): OS Keychain — الـ DB يخزن reference فقط
server headless:
   • SecretFile مشفر: state خلف passphrase يقدمه المشغل عند الإقلاع
     (Argon2id من الـ passphrase → AES-256-GCM على ملف secrets)
   • يعمل أيضاً: متغير بيئة ONE-SHOT عند التشغيل الأول فقط (seed),
     ثم يُخزن مشفراً — لا يبقى في البيئة
القواعد الثابتة (في الحالتين):
   • DB يخزن مرجعاً لا قيمة — أبداً
   • قراءة سر = حدث في audit_log (من، ماذا، متى) — بلا قيمة السر نفسه
   • export/import vpkg يستثني الأسرار حصراً (يُعاد إدخالها في الوجهة)
```

**العواقب:** إيجابية: daemon mode يعمل من أول إصدار بلا شق أمني، تدقيق قراءة كامل. سلبية: خادم بلا تفاعل يحتاج الآلية أعلاه في systemd unit أو إدخال أول تشغيل — موثق كإجراء تشغيل في المرحلة 3.

**قاعدة الفحص:** فحص CI: صفوف `settings` وكل الجداول لا تحتوي أنماط مفاتيح API معروفة (sk-, api key patterns). اختبار A3-T4: محاولة قراءة سر غير مرخص → رفض + صف audit_log.

### ADR-017 — Context Compiler: وحدة صريحة صاحبة الـ Prompt

**الحالة:** مقرَّر · **التصنيف:** سدّ · **يغلق:** G-10

**السياق:** سؤال لم يُجب عنه في أي وثيقة سابقة: **من يبني الـ prompt النهائي؟** في التصاميم اللامحددة، كل وكيل يلصق ما يريد: skill كاملة تُحقن دفعة واحدة، ذكريات تختار نفسها، سياسات تُنسى. النتيجة المعروفة: تضخم context، تضارب تعليمات، وسقف 50K token لمهارة واحدة كما حذرت وثيقة الـ Stack من progressive loading دون تعريف آليته الملزمة.

**البدائل المدروسة:**

| البديل | سبب الرفض |
|---|---|
| كل وكيل يبني prompt بنفسه | تغاير بلا سقف؛ لا قياس، لا حد أقصى، لا تدقيق |
| قالب نصي ثابت | يتجاهل هوية المهمة والذاكرة المتاحة والسياسات — prompt ميت |
| حقن كل شيء متاح | يتناقض صراحة مع progressive disclosure وحسابية الأجهزة الضعيفة |

**القرار:** `ContextCompiler` وحدة في `vara-core` هي **المصنع الحصري** لمحتوى كل استدلال:

```text
مدخلاته (كلها من مصادر ملزمة):
   identity(الوكيل) + mission snapshot + skill slices (progressive)
 + memory_hits (نتائج ADR-013) + policies الحاكمة + tool manifest مقتطفاً
 + budget state + حصة الصوت البشري الأخيرة
مخرجاته:
   prompt نهائي + manifest شفاف: من أين جاء كل جزء وبأي أولوية
قواعد الملزمة:
   • ميزانية context لكل استدلال (tokens) — تجاوزها = قص حسب الأولوية المعرفة
     (policies > mission > identity > skills slices > memory > history)
   • skill slice وحيد لكل استدلال — لا حقن skill كاملة أبداً
   • كل prompt يُسجل مجزأً في events (hashes الأجزاء لا النصوص الكاملة) — تدقيق لاحق
```

**العواقب:** إيجابية: سقف تكلفة معروف لكل استدلال، تدقيق "لماذا رأى النموذج هذا؟"، تقييم معزول لجودة التجميع. سلبية: انضباط إضافي على كل مسار استدلال — يقابله أن الـ Compiler يصبح أفضل نقطة قياس وتحسين في النظام كله.

**قاعدة الفحص:** اختبار GM-2: مهمة بحث ثنائية الوكلاء — كل استدلال له manifest شفاف كامل، وصفر استدلال يتجاوز ميزانية context المعلنة. وأي `format!` يبني prompt خارج الـ Compiler يُرفض بمراجعة الكود (checklist).

### ADR-018 — Model Manager: مالك دورة حياة النماذج

**الحالة:** مقرَّر · **التصنيف:** سدّ · **يغلق:** G-11

**السياق:** نماذج llama.cpp تقاس بالجيجابايتات، والتحميل يفشل في منتصفه، والمساحة تنفد، وملف تالف يجعل الفشل غامضاً "النموذج لا يستجيب". وثيقة الـ Stack استهدفت hardware-aware routing بلا أن تعلن: **من يملك تحميل النماذج والتحقق منها وحذفها؟** غياب هذا المالك = ساعات تشخيص يضيعها المستخدم وتشوّه أول انطباع عن المنتج.

**البدائل المدروسة:**

| البديل | سبب الرفض |
|---|---|
| تحميل يدوي خارجي (المستخدم ينزل الملف) | يكسر "double click" — قرار محسوم في وثيقة الـ Stack نفسها |
| تحميل مباشر في الـ Gateway عند أول استدعاء | استدلال أول بطيء وعشوائي؛ لا تحقق checksum؛ لا مساحة محجوزة |
| Ollama كلوحة إدارة نماذج | يربط إدارة دورة الحياة بمزود — يخالف "الذكاء قابل للاستبدال" |

**القرار:** `model-manager` داخل `vara-gateway` مسؤول حصري عن: سجل النماذج (`model_registry` بأسماء أدوار: `l1_tiny / l2_general / l3_heavy / embedding`)، التحميل القابل للاستكمال (resumable chunks + checksum sha256 قبل التفعيل)، حجز المساحة (فحص disk قبل البدء + إحباط نظيف)، والـ GC: حذف مرشح للنماذج غير المستعملة فوق 60 يوماً **بموافقة صريحة**. التوصية الابتدائية للأجهزة: جدول profiles مبني على hardware profile (رام/VRAM) يُمسح عند أول إقلاع — نفس جدول أولويات وثيقة الـ Stack، الآن موثق وسجل.

**العواقب:** إيجابية: أول تشغيل موثوق، فشل قابل للتسمية (`ChecksumMismatch` لا "لا يستجيب")، سجل مركزي يقرأ منه الـ routing. سلبية: كود إدارة إضافي — يقتلع أضعافه من دعم المستخدم المتجنّب.

**قاعدة الفحص:** اختبار A0-T2: تحميل مقطوع في منتصفه → استكمال بنجاح، وملف checksum خاطئ → رفض تفعيل + حدث مسمى. وأي قراءة مسار نموذج خارج `model-manager` تُرفض بمراجعة الكود.

### ADR-019 — Daemon Mode مصادَق من اليوم الأول

**الحالة:** مقرَّر · **التصنيف:** سدّ · **يغلق:** G-12

**السياق:** "https://your-server/vara" من وثيقة الـ Stack فكرة النقل الحية — لكن الكيان المكشوف عبر شبكة يستطيع **تنفيذ كود على جهازك**. كل ثانية بلا مصادقة في v1 ليست "ميزة مؤجلة"، بل سطح هجوم مفتوح على قدرات نشر/ملفات/أسرار. الافتراض الخطير: "الشبكة المنزلية آمنة" لم يعد افتراضاً هندسياً.

**البدائل المدروسة:**

| البديل | سبب الرفض |
|---|---|
| HTTP مفتوح على LAN "مؤقتاً" | سطح هجوم من اليوم الأول؛ "المؤقت" لا يموت أبداً |
| Basic Auth | أسرار ضعيفة التشفير في الترانزيت؛ لا إبطال جلسات |
| VPN/Tailscale كمتطلب | ممتاز كطبقة إضافية، غير مقبول كـ**بديل** عن مصادقة التطبيق نفسه |
| تسجيل دخول مستخدم كامل (OAuth) | أثقل من حاجة v1 — API شخصي على جهاز واحد |

**القرار:** في المرحلة 3 (عند أول build لوضع daemon) يُلزم:

```text
• Token Bearer عشوائي 32+ بايت يُولد عند أول إقلاع، يُخزن عبر SecretStore (ADR-016)
• Bind الافتراضي: 127.0.0.1 فقط — فتح 0.0.0.0 قرار صريح بعلم + تحذير في الـ CLI
• TLS خارج النطاق المحلي شرط (توثيق reverse proxy جاهز بـ Caddy/Nginx)
• إبطال token وإعادة توليد بأمر CLI واحد (vara auth rotate)
• كل طلب مرفوض/مقبول = صف في audit_log
• SSE/WebSocket بنفس التوكن — لا استثناء للـ streaming
```

**العواقب:** إيجابية: قابلية النقل تبدأ آمنة، إبطال فوري عند التسريب، تدقيق كامل. سلبية: خطوة إعداد إضافية للواجهة البعيدة — توثق في 3 أسطر داخل docs التشغيل.

**قاعدة الفحص:** اختبار A3-T5: كل مسارات API بلا token → 401 حتماً، وباستثناء المسار الصحي (`/health`) — يُفحص مولداً آلياً من قائمة الـ routes، وbind خارج localhost بلا علم = رفض إقلاع.

### ADR-020 — Eval Harness: المهام الذهبية كحارس انحدار دائم

**الحالة:** مقرَّر · **التصنيف:** سدّ · **يغلق:** G-13

**السياق:** أخطر خاصية في Vara هي أيضاً أخطر ثغرته: الحلقة الديناميكية (plan → create → execute → replan) **لا تملك متوازياً وحدوياً**. أي تعديل في الـ Compiler أو الـ Gateway أو صياغة agent loop يمكن أن يكسر سلوكاً بعيداً بصمت — يُكتشف بعد أسابيع كـ"النتائج صارت أسوأ" بلا سبب قابل للإسناد. بدون حارس، كل تحسين = مقامرة على كل ما قبله.

**البدائل المدروسة:**

| البديل | سبب الرفض |
|---|---|
| اختبارات وحدة فقط | تختبر القطع لا السلوك المنبثق — وهنا السلوك هو المنتج |
| مراجعة بشرية يدوية لكل إصدار | لا تتناسب؛ ذاتية؛ تتعب وتتوقف |
| LLM-as-judge وحده في CI | مفيد كطبقة، غير كافٍ وحده: حكمه غير حتمي وكلفته تتراكم |

**القرار:** `vara-eval` — جناح مهام ذهبية (Golden Missions) يُشغل محلياً وعلى كل PR يؤثر على المسار الاستدلالي:

```text
GM-1  مهمة بحث وحدة (بحث سوق → تقرير منظم)          [مرحلة 1]
GM-2  بحث ثنائي الوكلاء (researcher + analyst + handoff) [مرحلة 2]
GM-3  انهيار قسري واستئناف منتصف مهمة                  [مرحلة 1]
GM-4  ميزانية ضيقة → توقف موثق بلا تجاوز               [مرحلة 2]
GM-5  إعادة مهمة مشابهة → أسرع/أرخص بذاكرة + genome    [مرحلة 2+]
GM-6  اختبار الفرضية: وكيل واحد vs فريق ديناميكي — نفس المهمة ونفس الميزانية [مرحلة 2، شرط إغلاق حاكم]
```

حكامة النتيجة ثلاث طبقات: (1) فحوص حتمية صارمة — الملفات وُجدت، لا تجاوز ميزانية، صفر tool call غير مسجل، (2) بنية مخرجات مطابقة schema، (3) طبقة LLM-judge محدودة بـ rubric نصي مع مقارنة بـ baseline محفوظ (منشور في artifacts كل تشغيل) — **الحكم على الفارق لا على الجودة المطلقة**. أي انحدار فوق عتبة معلنة يمنع الدمج. نتائج كل تشغيل تُخزن في `eval_runs` فتصبح المنحنى الزمني لصحة الكيان.

**العواقب:** إيجابية: كل تحسين قابل للإسناد، ثقة بالتكرار السريع، منحنى جودة معروض في الواجهة لاحقاً كعامل ثقة. سلبية: كلفة استدلالات في CI — تُدار بمحاكاة Gateway (`MockProvider` بأجوبة مثبتة) للفحوص البنيوية، والاستدلال الحقيقي ليلياً أو يدوياً.

**قاعدة الفحص:** CI Gate: فشل GM حتمي = منع دمج؛ وأي تعديل على المسار الاستدلالي بلا تشغيل eval موثق = رفض PR (checklist مراجعة).

### ADR-021 — الواجهة Projection: لا حالة حقيقية في الـ UI

**الحالة:** مقرَّر · **التصنيف:** سدّ · **يغلق:** G-14

**السياق:** واجهة كيان حي تعرض "شجرة تنظيم تنفس" — الأخطر فيها أن تظهر حالة **تختلف عن الحقيقة** (وكيل معروض شغّال وهو مات، ميزانية معروضة أقدم من الواقع). هذا يحدث حتماً إذا احتفظت الواجهة بحالتها الخاصة وتزامنت "عند التحديث". وثيقة الـ Stack بنت Event Bus صحيحاً — القرار الناقص هو إلزام الواجهة بكونه **مصدرها الوحيد**.

**البدائل المدروسة:**

| البديل | سبب الرفض |
|---|---|
| UI يبني حالته ويستعلم دورياً | اختلاف مزامنة حتمي؛ حالة وهمية في لحظات الانقطاع |
| حالة مزدوجة (bus + polling للتصحيح) | مصدرا حقيقة = لا مصدر حقيقة؛ أخطاء سباق بعيدة التشخيص |
| كاش UI دائم في localStorage | يظهر بيانات كيان من جهاز/زمن آخر — خطر ثقة وخصوصية |

**القرار:** الواجهة **دالة حتمية من سجل الأحداث**:

```text
events (SQLite / WebSocket stream)
   ↓  (حتمي، قابل لإعادة التشغيل من أي نقطة)
Svelte Stores (projection واحد لكل منطقة: org-tree, activity, budgets, memory-browser)
   ↓
عرض
القواعد:
• الإقلاع: snapshot واحد للحالة (GET /state/bootstrap) ثم الأحداث بعده فقط
• انقطاع الاتصال = شريط "غير متصل" + إعادة التزامن من آخر seq — لا كاش صامت
• كل أمر (pause/kill/تغيير policy) = إرسال أمر → يُعاد ظهوره كحدث —
  الواجهة لا "تعرف" النتيجة قبلاً
```

**العواقب:** إيجابية: انسجام مضمون معروض/واقع، إعادة تزامن حتمية، إمكانية "تشغيل الجلسة كفيلم" (replay من events) — ميزة تدقيق فريدة تعود لعقدها فلسفة الشفافية في الرؤية. سلبية: الانقطاعات الطويلة تعيد رسم الكل بعد الإقلاع — مقبول لواجهة إشراف.

**قاعدة الفحص:** اختبار A3-T6: أثناء مهمة حية، أخفِ حالة في الـ DB (وكيل توقف) — يجب أن يعكس العرض ذلك خلال ≤ ثانية من بث الحدث، واختبار إعادة تزامن: قطع الاتصال 10s مع 50 حدثاً وسيطاً → العرض مطابق حتمياً بعد الاستئناف.

### ADR-022 — Content-Addressed Storage: sha256 هو هوية الملف

**الحالة:** مقرَّر · **التصنيف:** سدّ · **يغلق:** G-15 · **يثبت:** قرار الـ Stack رقم 10

**السياق:** وثيقة الـ Stack حددت الشكل (objects/sha256/) دون **عقد الاستخدام**. بدون عقد ملزم، يبدأ كل قسم بوضع ملفاته كما يحلو: تقرير في مجلد المهمة، نسخة في مجلد الوكيل، مرفق في cache — والنتيجة: تكرار، export هش، و"احذف المهمة القديمة" يصبح حفراً أثرياً.

**البدائل المدروسة:**

| البديل | سبب الرفض |
|---|---|
| ملفات مسماة في مجلدات منطقية | نفس الملف × 3 مواضع؛ الحذف الآمن مستحيل |
| BLOBs داخل SQLite | تضخيم DB وإبطاء كل شيء — يخالف فصل وثيقة الـ Stack |
| مراجع مسارات نصية حرة | تكسر عند النقل (portability) — جوهر المنتج |

**القرار:** عقد ثلاثي ملزم:

```text
1. كل ملف > 64KB (تقرير، مرفق، لقطة متصفح، artifact مهارة) يُخزن:
      objects/ab/abcdef1234...   (شاردتان أوليان من sha256)
   ويُرجع مرجعاً {sha256, size, mime} — لا يُكتب مسار نصي في أي مكان
2. الوجود قبل المرجع: تُكتب البيانات وتُحسب الـ hash قبل أي صف في artifacts
   (لا مرجع لملف غير موجود — سلامة بنيوية)
3. الحذف بمجمّع (GC): صفوف artifact_refs هي عقد الحياة —
   لا يُحذف object إلا بلا مراجع، وبعد فترة سماح 7 أيام، وبحدث ArtifactGCDone
```

هذا يجعل: التكرار صفراً بنيوياً، export = اجتياز المراجع، وsalvage بعد انهيار DB ممكناً من الملفات وحدها.

**العواقب:** إيجابية: سلامة تحقق ذاتي (hash مكسور = تلف معلن لا صمت)، نقل مضمون، إزالة توأمية مجانية. سلبية: مجلد objects لا يُفهم يدوياً — يعالجه `vara fs inspect` بسيط في الـ CLI (المرحلة 1).

**قاعدة الفحص:** اختبار A1-T1: كتابة نفس التقرير في مهمتين → صف object واحد حصراً؛ وحذف المهمتين + GC → object مُحذف؛ مرجع لملف مفقود (تلف يدوي) → كشف فوري عند أول `fs verify` ولا صمت.

# الجزء الثاني — Schema الكامل: `0001_init.sql`

هذا الـ DDL جاهز للتنفيذ كما هو (مع جاهزية تعديل أسماء أقل من 5%). المبادئ الحاكمة:

- **المعرفات:** `TEXT` = ULID (مرتبة زمنياً، صالحة للتشابك بين الجداول). **الزمن:** ISO-8601 UTC نصاً. **JSON:** نص مع دوال `json_()` متاحة للفحص.
- **كل جدول يخدم قراراً معروفاً** — لا جدول "للأمان". التعلق بـ ADR مكتوب في كل كتلة.
- **append-only مفروض بالـ triggers** — لا ثقة بالانضباط الفردي (قواعد لا تُكسر رقم 6).
- تُنفَّذ عبر نظام migrations في `vara-state` (`schema_migrations`) — لا `CREATE TABLE` خارج ملفات migration.

```sql
-- ============================================================================
-- 0001_init.sql — Vara State Schema v1
-- مبادئ: ADR-005 (SQLite+WAL), ADR-009 (كاتب وحيد), ADR-010 (mailbox دائم),
--        ADR-011 (events+checkpoints), ADR-014 (ledger), ADR-022 (CAS)
-- ============================================================================

-- ---------------------------------------------------------------------------
-- 0. النظام
-- ---------------------------------------------------------------------------
CREATE TABLE schema_migrations (
    version     INTEGER PRIMARY KEY,
    applied_at  TEXT    NOT NULL,
    description TEXT    NOT NULL
);

CREATE TABLE settings (                              -- تهيئة الكيان فقط
    key         TEXT PRIMARY KEY,
    value       TEXT NOT NULL,                       -- أسرار ممنوعة هنا (ADR-016)
    updated_at  TEXT NOT NULL
);

CREATE TABLE hardware_profile (                      -- أساس model routing (Stack §16)
    id          TEXT PRIMARY KEY,
    ram_gb      REAL NOT NULL,
    cpu_cores   INTEGER NOT NULL,
    gpu_name    TEXT,
    vram_gb     REAL,
    os          TEXT NOT NULL,
    npu         TEXT,
    tier        TEXT NOT NULL CHECK (tier IN ('minimal','low','mid','high')),
    profiled_at TEXT NOT NULL
);

-- ---------------------------------------------------------------------------
-- 1. الهوية والوكلاء  (ADR-004, ADR-010)
-- ---------------------------------------------------------------------------
CREATE TABLE identities (
    id            TEXT PRIMARY KEY,
    name          TEXT NOT NULL,
    role          TEXT NOT NULL,
    system_prompt TEXT NOT NULL,
    traits_json   TEXT NOT NULL DEFAULT '{}',
    risk_tolerance TEXT NOT NULL DEFAULT 'medium'
                  CHECK (risk_tolerance IN ('low','medium','high')),
    source        TEXT NOT NULL DEFAULT 'builtin'
                  CHECK (source IN ('builtin','vara_created','user')),
    created_at    TEXT NOT NULL
);

CREATE TABLE agents (
    id              TEXT PRIMARY KEY,
    kind            TEXT NOT NULL CHECK (kind IN ('root','specialist','manager')),
    identity_id     TEXT NOT NULL REFERENCES identities(id),
    parent_agent_id TEXT REFERENCES agents(id),      -- شجرة الإشراف (ADR-010)
    status          TEXT NOT NULL DEFAULT 'creating'
                    CHECK (status IN ('creating','idle','running','waiting',
                                      'suspended','terminated','failed')),
    restart_count   INTEGER NOT NULL DEFAULT 0,      -- عتبة supervision
    last_heartbeat  TEXT,
    created_at      TEXT NOT NULL,
    updated_at      TEXT NOT NULL,
    terminated_at   TEXT
);
CREATE INDEX idx_agents_status   ON agents(status);
CREATE INDEX idx_agents_parent   ON agents(parent_agent_id);

-- Mailbox الدائم: كل رسالة تُكتب قبل التسليم (ADR-010 — G-02)
CREATE TABLE agent_mailbox (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    agent_id      TEXT NOT NULL REFERENCES agents(id),
    seq           INTEGER NOT NULL,                  -- ترتيب لكل وكيل
    envelope_json TEXT NOT NULL,                     -- {from,type,priority,payload}
    priority      INTEGER NOT NULL DEFAULT 5,
    delivered     INTEGER NOT NULL DEFAULT 0,
    delivered_at  TEXT,
    created_at    TEXT NOT NULL,
    UNIQUE (agent_id, seq)
);
CREATE INDEX idx_mailbox_pending ON agent_mailbox(agent_id, delivered, priority);

-- ---------------------------------------------------------------------------
-- 2. المهام  (mission loop — وثيقة الرؤية)
-- ---------------------------------------------------------------------------
CREATE TABLE missions (
    id            TEXT PRIMARY KEY,
    title         TEXT NOT NULL,
    objective     TEXT NOT NULL,
    constraints_json      TEXT NOT NULL DEFAULT '[]',
    success_criteria_json TEXT NOT NULL DEFAULT '[]',
    risk_boundaries_json  TEXT NOT NULL DEFAULT '[]',
    status        TEXT NOT NULL DEFAULT 'draft'
                  CHECK (status IN ('draft','planning','executing','blocked',
                                    'paused','completed','failed','cancelled')),
    budget_id     TEXT REFERENCES budgets(id),
    failure_note  TEXT,                              -- "لماذا توقف/فشل" إجبارية عند الفشل
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL,
    completed_at  TEXT
);
CREATE INDEX idx_missions_status ON missions(status);

CREATE TABLE tasks (
    id                TEXT PRIMARY KEY,
    mission_id        TEXT NOT NULL REFERENCES missions(id),
    parent_task_id    TEXT REFERENCES tasks(id),
    title             TEXT NOT NULL,
    description       TEXT,
    status            TEXT NOT NULL DEFAULT 'pending'
                      CHECK (status IN ('pending','ready','running','blocked',
                                        'done','failed','cancelled')),
    priority          INTEGER NOT NULL DEFAULT 5,
    deadline          TEXT,
    dependencies_json TEXT NOT NULL DEFAULT '[]',
    assigned_agent_id TEXT REFERENCES agents(id),
    created_at        TEXT NOT NULL,
    updated_at        TEXT NOT NULL
);
CREATE INDEX idx_tasks_mission ON tasks(mission_id, status, priority);
CREATE INDEX idx_tasks_agent   ON tasks(assigned_agent_id, status);

-- ---------------------------------------------------------------------------
-- 3. التنظيم  (teams ديناميكية — وثيقة الرؤية §Organizations)
-- ---------------------------------------------------------------------------
CREATE TABLE teams (
    id           TEXT PRIMARY KEY,
    mission_id   TEXT REFERENCES missions(id),       -- NULL = بنية دائمة
    name         TEXT NOT NULL,
    kind         TEXT NOT NULL CHECK (kind IN ('builtin','dynamic','temporary')),
    status       TEXT NOT NULL DEFAULT 'active'
                 CHECK (status IN ('active','dissolved')),
    created_at   TEXT NOT NULL,
    dissolved_at TEXT
);

CREATE TABLE team_members (
    team_id      TEXT NOT NULL REFERENCES teams(id),
    agent_id     TEXT NOT NULL REFERENCES agents(id),
    role_in_team TEXT NOT NULL,
    joined_at    TEXT NOT NULL,
    PRIMARY KEY (team_id, agent_id)
);

-- الذاكرة التنظيمية: كل تغيير بنيوي = صف (المصدر: "المنظمة تتطور")
CREATE TABLE org_changes (
    id          TEXT PRIMARY KEY,
    team_id     TEXT REFERENCES teams(id),
    change_type TEXT NOT NULL CHECK (change_type IN
        ('create','merge','split','assign','reassign','suspend',
         'terminate','replace','dissolve')),
    payload_json TEXT NOT NULL,
    reason      TEXT NOT NULL,                       -- لا تغيير بلا سبب موثق
    created_at  TEXT NOT NULL
);
```

**ملاحظة تنفيذية (1/2):** جدول `agent_mailbox` هو قلب ADR-010 — لاحظ أن `delivered` علم فقط، والاستئناف يقرأ `seq > last_delivered_seq` المحفوظ في حالة الوكيل. حذف الرسائل المسلّمة مهمة تنظيف مؤجلة (بعد 30 يوماً + أرشفة الأهم)، لا فوري.

```sql
-- ---------------------------------------------------------------------------
-- 4. المهارات  (Skill lifecycle — Draft→Sandboxed→Tested→Trusted)
-- ---------------------------------------------------------------------------
CREATE TABLE skills (
    id                 TEXT PRIMARY KEY,
    name               TEXT NOT NULL UNIQUE,
    current_version_id TEXT,                         -- FK مؤجل (version يُنشأ بعدها)
    trust_origin       TEXT NOT NULL DEFAULT 'builtin'
                       CHECK (trust_origin IN ('builtin','community','self_created')),
    created_at         TEXT NOT NULL
);

CREATE TABLE skill_versions (
    id                TEXT PRIMARY KEY,
    skill_id          TEXT NOT NULL REFERENCES skills(id),
    version           TEXT NOT NULL,                 -- semver
    manifest_json     TEXT NOT NULL,                 -- العقد الكامل (انظر الملحق 9.1)
    instructions_path TEXT,                          -- نسبة داخل حزمة المهارة
    state             TEXT NOT NULL DEFAULT 'draft'
                      CHECK (state IN ('draft','sandboxed','testing',
                                       'trusted','deprecated','archived')),
    risk_level        TEXT NOT NULL DEFAULT 'medium'
                      CHECK (risk_level IN ('low','medium','high','critical')),
    origin_note       TEXT,                          -- أي مهمة/سبب أنشأها (self_created)
    test_summary_json TEXT NOT NULL DEFAULT '{}',    -- إيصالات الاختبارات الثلاثة (ADR-015)
    created_at        TEXT NOT NULL,
    promoted_at       TEXT,
    UNIQUE (skill_id, version)
);
-- تفعيل الـ FK المؤجل بعد التعريف:
-- (يُنفذ في migration كتحديث بعد إنشاء أول version — أو يُدار بالمستوى التطبيقي)

CREATE TABLE skill_dependencies (
    skill_version_id     TEXT NOT NULL REFERENCES skill_versions(id),
    depends_on_skill_id  TEXT NOT NULL REFERENCES skills(id),
    min_version          TEXT,
    PRIMARY KEY (skill_version_id, depends_on_skill_id)
);

CREATE TABLE skill_tests (
    id               TEXT PRIMARY KEY,
    skill_version_id TEXT NOT NULL REFERENCES skill_versions(id),
    name             TEXT NOT NULL,
    kind             TEXT NOT NULL CHECK (kind IN ('synthetic','replay','eval_suite','manual')),
    status           TEXT NOT NULL CHECK (status IN ('passed','failed','error')),
    result_json      TEXT NOT NULL,
    ran_at           TEXT NOT NULL
);
CREATE INDEX idx_skill_tests_version ON skill_tests(skill_version_id, ran_at);

-- ---------------------------------------------------------------------------
-- 5. الذاكرة  (Hybrid — Structured + FTS5 + Vector, ADR-013)
-- ---------------------------------------------------------------------------
CREATE TABLE memories (
    id               TEXT PRIMARY KEY,
    kind             TEXT NOT NULL CHECK (kind IN
                     ('episodic','semantic','procedural','project',
                      'relational','world_state','identity','capability')),
    content          TEXT NOT NULL,
    agent_id         TEXT REFERENCES agents(id),
    mission_id       TEXT REFERENCES missions(id),
    project_id       TEXT,
    source           TEXT NOT NULL DEFAULT 'agent',  -- مصدر الذكرى (تدقيق)
    confidence       REAL NOT NULL DEFAULT 0.7
                     CHECK (confidence BETWEEN 0 AND 1),
    importance       REAL NOT NULL DEFAULT 0.5
                     CHECK (importance BETWEEN 0 AND 1),
    supersedes_id    TEXT REFERENCES memories(id),   -- "الذاكرة ≠ الحقيقة": تصحيح لا حذف
    status           TEXT NOT NULL DEFAULT 'active'
                     CHECK (status IN ('active','superseded','archived','deleted')),
    created_at       TEXT NOT NULL,
    last_verified_at TEXT,                           -- ترويج الميتاداتا (Stack §ذاكرة/حقيقة)
    expires_at       TEXT,                           -- مراجعة/انتهاء اختياري
    review_condition TEXT
```

## 5.5 مقتطف Persistence Actor (الجوهر التنفيذي لـ ADR-009)

```rust
pub async fn run(mut rx: mpsc::Receiver<WriteReq>, db: WriteConn) {
    let mut batch: Vec<WriteReq> = Vec::with_capacity(64);
    loop {
        // أول طلب ينتظر، ثم تصريف متوفر خلال نافذة 25ms — لا مؤقت دائم بلا عمل
        let first = match rx.recv().await { Some(r) => r, None => break };
        batch.push(first);
        while batch.len() < 64 {
            match tokio::time::timeout(Duration::from_millis(25), rx.recv()).await {
                Ok(Some(r)) => batch.push(r),
                Ok(None) => break,
                Err(_elapsed) => break,
            }
        }
        let tx = db.conn.transaction().expect("tx");
        for req in &batch { apply(&tx, req); }          // ترتيب أولوية محفوظ بالقناة
        tx.commit().expect("commit");
        for req in batch.drain(..) { req.ack(); }       // إيصالات oneshot للكتّاب
    }
}
```

# الجزء الرابع — خطة MVP: أربع مراحل بمعايير قبول قابلة للقياس

**منهجية الخطة:** لا أزمنة تقديرية — المرحلة تُغلق عند إتمام كل بنود Definition of Done واجتياز سيناريو القبول كاملاً. **قاعدة صارمة:** لا تبدأ مرحلة قبل إغلاق سابقتها؛ والمرحلة قد "تُبتر" (cut scope) لكن لا تُهمل (skip). سيناريوهات القبول كلها على جبهة **مهام البحث والتحليل**.

> **بوابة ما قبل المرحلة 0 (مضافة v1.1):** قبل بناء أي بنية دائمة، **نموذج رمي (throwaway)** — سكربت واحد بلا ADRs ولا مستودع — يجري GM-6 مصغرة: نفس مهمة البحث، نفس سقف الميزانية، مرة بوكيل واحد ومرة بفريق مصغر (researcher + analyst)، وتقييم الجودة بروبريك يدوي معلن. الفريق يتفوق بوضوح → تبدأ المرحلة 0 كما هي. غير ذلك → تعديل جوهر الفكرة قبل بناء 22 قراراً حولها. النموذج الرمي نفسه لا يدخل المستودع — نتائجه وحدها تُحفظ.

## المرحلة 1 — الحلقة الواحدة (The Single Loop)

**الهدف:** جوهر Vara بحجمه الأصغر: وكيل واحد يستقبل مهمة، يخطط، ينفذ بأداة، يتذكر، وينجو من الانهيار. **هذه المرحلة هي المشروع كله بحجم مصغر** — كل ما بعدها تراكم فوقها.

**النطاق الداخل:**

- `vara-core`: actor system + mailbox دائم (ADR-010) + supervision أساسي (restart ×3 → escalate) + checkpoints دلالية (ADR-011)
- `ContextCompiler` (ADR-017): identity + mission + skill slice + memory hits + policies
- `vara-memory`: put/query بالـ FTS5 + ميتاداتا (الأهمية/الحداثة) — **بدون vector بعد**
- `vara-skills`: تحميل حزمة مهارة (manifest + instructions) بـ progressive slices
- `vara-tools`: registry + عقد الإلغاء الكامل + أداة `filesystem.read` + أداة `web.fetch` (خارج sandbox — builtin درجة 0)
- `vara-policy`: policies (allow/deny/ask) + audit_log
- مهارة مدمجة واحدة: `research-basic` (بحث موضوع → تقرير منظم مرجعي المصادر)
- `vara-cli`: `vara mission run "..."` · `vara mission status` · `vara fs verify`

**غير النطاق:** إنشاء وكلاء إضافيين، إنشاء مهارات ذاتي، vector search، واجهة رسومية، daemon mode.

**Definition of Done:**

- [ ] A1-T1: مهمة بحث وحدة تكتمل من CLI → تقرير markdown في objects + صف artifact_ref + ذكريات من نوع episodic/semantic محفوظة
- [ ] A1-T2 (الانهيار): kill -9 في منتصف مهمة → إعادة تشغيل → `vara mission resume` → تكتمل، لا رسالة ضائعة في mailbox، لا تنفيذ مكرر لأداة غير idempotent
- [ ] A1-T3 (الإلغاء النظيف): إلغاء مهمة أثناء `web.fetch` طويلة → العملية/الاتصال يُغلق، `ToolCancelled{cleanuped:true}`، المهمة تنتقل لحالة موثقة
- [ ] السياسة: أمر قراءة خارج مسار مسموح → رفض + صف audit_log + استمرار المهمة برسالة للوكيل
- [ ] الذاكرة: إعادة المهمة نفسها بعد تعديل المحتوى → الـ context يحوي ذكريات الجولة الأولى (يُثبت بمحتوى manifest الـ Compiler)
- [ ] كل استدلال له context manifest كامل + لم يتجاوز سقف tokens المعلن
- [ ] GM-1 و GM-3 (من ADR-020) يجتازان محلياً

**سيناريو القبول A1 (يدوي، 15 دقيقة):**

```text
A1-T1 vara mission run "ابحث عن تطور أسعار الفائدة الأمريكية آخر 12 شهراً وأنتج تقريراً مرجعياً"
      → AgentCreated → ToolStarted(web.fetch) ×N → تقرير في objects
      → vara memory list تظهر ذكريات بأهميات مختلفة
A1-T2 أثناء مهمة ثانية: kill -9 vara (قسري)
      → vara daemon (تشغيل جديد) → vara mission list تظهر المهمة executing (stale)
      → vara mission resume → تُستأنف من آخر checkpoint → تكتمل
      → vara events --since <kill_ts> تُظهر كامل القصة بلا فجوات
A1-T3 vara mission cancel أثناء fetch مستمر
      → خلال ≤ 5 ثوانٍ: لا عملية يتيمة (فحص OS)، ToolCancelled مع cleanuped=true
```

## المرحلة 2 — التكاثر (Multiplication)

**الهدف:** أول وعد حقيقي من وثيقة الرؤية: **Vara يقرر أن يحتاج وكيلاً ثانياً**، يكوّنه، يتخاطب معه، ويعيد تشكيل الفريق عند الحاجة — تحت اقتصاد مُفرض.

**النطاق الداخل:**

- `vara-agents`: spawn وكلاء specialists (identities مركبة: identity + skills + tools + budget) + إغلاق حلقة الـ mailbox بينهم
- `vara-org`: فرض dynamic/temporary + org_changes (كل تغيير بنيوي بسؤال "لماذا")
- `vara-scheduler`: أولويات + caps حسب hardware_profile (مثال 8GB: expensive متزامن = 1، cheap = 4) + resource manager قبل كل spawn (`هل أستطيع الآن؟`)
- `vara-memory`: تفعيل sqlite-vec اختياري + دمج RRF الثلاثي (ADR-013) + embedding_queue الخامل
- ميزانيات ملزمة لكل مهمة/وكيل (ADR-014) + تقرير تكلفة المهمة في CLI
- mission genome v0: هيكل فريق المهمة الناجحة يُحفظ كذكريات capability (بلا محرك إعادة بناء كامل بعد — التسجيل فقط)
- مهارة ثانية مدمجة: `web-search` (بحثاً منظماً متعدد الاستعلامات)

**غير النطاق:** إنشاء مهارات ذاتي، sandbox subprocess، واجهة رسومية، daemon، export.

**Definition of Done:**

- [ ] A2-T1: مهمة "بحث سوق + تحليل تنافسي" → Vara ينشئ Researcher ثم Analyst استجابة لحاجة حقيقية (ليس من قائمة مسبقة) → تبادل رسائل موثق في mailbox → تقرير مدمج
- [ ] Scheduler: محاكاة جهاز 8GB → لا يتجاوز الـ caps تحت ضغط 10 مهام متزامنة (اختبار)
- [ ] A2-T3 (RRF): eval استرجاع على ≥ 10 آلاف ذكرى مثبتة — RRF يتفوق على lexical فقط بفارق موثق، p95 ≤ 150ms
- [ ] A2-T2 (الاقتصاد): مهمة بميزانية tokens محدودة → عند الاستنفاد: `BudgetExhausted`، توقف نظيف، تقرير حالة موثق، **صفر تجاوز** (سباق 5 وكلاء على ميزانية 3 = 3 حصراً)
- [ ] إعادة تشكيل: فشل Analyst مرتين → قرار إشرافي معلن (إعادة/استبدال) في org_changes — لا صمت
- [ ] GM-2 و GM-4 و GM-5 يجتازون
- [ ] **GM-6 — شرط الإغلاق الحاكم للمرحلة (مضاف v1.1):** نفس مهمة A2-T1 حرفياً، نفس سقف tokens حرفياً — تشغيلان: **وحدة الوكيل (baseline دائم)** ثم الفريق الديناميكي. التقييم بروبريك معلن مسبقاً (أدناه)، محكوم يدوياً على العينة نفسها. **القرار المسبق المُلزم (مُلتزم به الآن قبل معرفة النتيجة):** إذا خسر الفريق أو لم يتفوق بفارق معلن — تُعاد صياغة الفرضية التنظيمية قبل أي بناء إضافي (المرشح الافتراضي: الفريق عند حاجة موازية/تخصص مقيس موثق فقط)، عبر ADR جديدة `supersedes` تُعدل قرار التنظيم الديناميكي — لا تمديد لجدول لا يثبت قيمته.

**سيناريو القبول A2 (يدوي، 20 دقيقة):**

```text
A2-T1 vara mission run "قارن بين أداتي إدارة مشاريع X وY للفرق الصغيرة وأنتج توصية"
      → events: AgentCreated(Researcher) → AgentCreated(Analyst) → AgentMessage×N
      → vara org tree يعرض البنية الفعلية المنشأة + دوافعها (org_changes)
A2-T2 نفس المهمة بميزانية 20% من الطبيعية
      → توقف موثق عند الحد، مع أسباب ولقطات من ledger
A2-T3 vara eval run retrieval
      → جدول مقارنة RRF vs lexical-only محفوظ في eval_runs
```

## المرحلة 3 — الجزء الخطير (The Dangerous Part)

**الهدف:** الحلقة التي تميز Vara عن كل السوق: **خلق القدرة المفقودة ذاتياً** — بأمان قسري. ثم القشرة الظاهرة: واجهة، daemon، ونقل.

**النطاق الداخل:**

- `vara-skills` + `vara-sandbox`: خط إنتاج إنشاء المهارة كاملاً:
  `Mission → SkillRequested (جواز إنشاء المهارة) → Draft (manifest + instructions + tests) → Sandboxed (درجة 1 — ADR-015) → 3 اختبارات (synthetic + replay) → Promote (v0.1.0) أو Reject مع السبب`
- أداة `skill.create` للـ L3 حصراً (لا تنشئ مهارات إلا الطبقة الثقيلة) + مراجعة إجبارية لمخرجات الاختبار
- Tauri 2 + Svelte 5 (ADR-021): org tree حي + activity stream + memory browser + budget panels
- `vara-daemon` (Axum): REST + SSE بمصادقة ADR-019 + bind الافتراضي localhost
- `vara export/import`: vpkg v1 (manifest + state.db + objects refs + skills) — يستثني الأسرار والنماذج (اختيارية)

**غير النطاق:** WASM sandbox، marketplace، مزامنة سحابية، computer-use، multi-user — قائمة الاستبعاد (الجزء السادس) تحكم.

**Definition of Done:**

- [ ] A3-T1 (الخطر المُروَّض — **بوابة إلزامية على Linux؛ موثق كقيد على Windows/macOS حسب مصفوفة ADR-015**): مهمة تحتاج مهارة غير موجودة → SkillRequested → تُبنى → تُختبر في sandbox بلا شبكة → **محاولة تنفيذ socket داخلها تفشل** بـ `SandboxViolation` → بعد إصلاح الاختبارات 3/3 → `SkillPromoted` بإيصالات. على Windows: مهارة self-created تعلن حاجة شبكة = رفض بنيوي مسبق (declarative فقط في v1)
- [ ] مهارة منشأة فشلت اختباراتها تبقى `draft` ولا تُستدعى أبداً (اختبار)
- [ ] A3-T5 (المصادقة): كل مسارات daemon بلا token = 401 (مولد آلياً من قائمة الـ routes)؛ `auth rotate` يُبطل القديم فوراً
- [ ] A3-T6 (الواجهة): حالة DB مخفاة → العرض يصحح ≤ 1s من بث الحدث؛ قطع اتصال 10s بـ 50 حدثاً وسيطاً → تطابق حتمي بعد الاستئناف
- [ ] A3-T4 (الأسرار): daemon على Linux headless بلا Secret Service → SecretFile مشفر يعمل؛ محاولة قراءة غير مرخصة → audit_log
- [ ] A3-T7 (النقل): `vara export` → مجلد جديد نظيف → `vara import` → الكيان يجيب عن "ماذا بحثنا الأسبوع الماضي؟" من ذاكرته المستوردة
- [ ] كل الـ 6 مهام ذهبية تجتاز + `vara eval` في CI على PR المسار الاستدلالي

## جدول المهام الذهبية (Golden Missions — ADR-020)

| ID | المهمة | المرحلة | الفحوص الحتمية الأساسية | ماذا يحمي |
|---|---|---|---|---|
| **GM-1** | بحث سوق وحدة → تقرير منظم مرجعي | 1 | **قاعدة بنيوية (معدّلة v1.2): كل رابط في التقرير ∈ مجموعة الروابط المسترجَعة فعلياً (نتائج بحث/صفحات مجلوبة) — فحص آلي خالص؛ وكل ادعاء رئيسي مرتبط بملاحظة مسترجَعة؛ صفر tool call غير مسجل، ذكريات محفوظة، تجاوز context صفر** — *القاعدة القديمة «مصادر ≥ 5» أُلغيت: كانت ستنجح تقريراً فيه 9/13 مصادر غير مسترجَعة (نموذج رمي v1)* | الحلقة الأساسية + Compiler + مدقق provenance |

| **GM-3** | انهيار قسري في منتصف مهمة + resume | 1 | صفر رسائل ضائعة، صفر تنفيذ مكرر لأداة irreversible، فجوات events = 0 | ADR-010/011 كاملة |
| **GM-4** | ميزانية ضيقة (20%) | 2 | `BudgetExhausted` قبل التجاوز، صفوف ledger متسقة مع السقف، تقرير توقف موثق | ADR-014 (الاقتصاد) |

**كلفة التشغيل:** GM-1..4 على MockProvider في كل PR (فحوص بنيوية) · GM-1..5 حقيقية ليلياً/يدوياً · GM-6 يدوي محكوم — يُشغَّل عند كل تغيير جوهري في منطق التنظيم وشهرياً على الأقل (حكمه جودة لا بنية) · baseline لكل تشغيل يُخزن كـ artifact — الحكم على **الفارق** دائماً.

## البطاقات التفصيلية

**R-01 — سرعة التكرار في Rust.** المفهوم يُبنى بالتجربة والخطأ في صياغة prompts وسلوك حلقات، وRust يجعل كل تجربة أبطأ من Python. *مؤشر مبكر:* نسبة تعديلات الـ prompts/skills إلى تعديلات الكود — إن قلّت الأولى عن الثانية، فالمنظومة تفرض كون التكرار في مكان خاطئ. *تخفيف:* منطق المهارات يعيش في Markdown/JSON (بلا إعادة بناء)، MockProvider يجعل دورة الاختبار ثوانٍ، والـ eval يحمي الجرأة على التعديل. *(v1.1: أثر رجعي مباشر — جعل ADR-001 "مؤقتة حتى نهاية المرحلة 1" بشرط تأكيد مقيس؛ الخطر لم يُحل بالتفاؤل بل بجدول استحقاق.)* *طوارئ:* عزل أكثر من المنطق التجريبي في مهارات + scripts قابلة للتحميل الحراري (بلا كود غير موثوق — درجات ADR-015 تحكم).

**R-02 — تذبذب النماذج المحلية.** على 8GB لن تكون جودة L2 مثالية. *مؤشر مبكر:* نتائج GM على MockProvider مستقرة لكن الحقيقية تتقلب > عتبة. *تخفيف:* L1 مقيدة (ADR-012)، المهارات تحدد خطوات صغيرة قابلة للتحقق، structured output إجباري، وسحابة **خيار** للمستخدم وليس شرط تشغيل. *طوارئ:* رفع الحد الأدنى للـ L2 الموصى به + توثيق عتبات الأجهزة بدقة، مع بقاء 2-4GB قيد التشغيل بجودة أقل معلنة.

**R-03 — تضخم النطاق.** كل مرحلة ستبدو "قابلة للتحسين" قبل إغلاقها. *مؤشر مبكر:* أي بند DoD مؤجل أسبوعين +. *تخفيف:* قاعدة "بتر لا تجاوز" مكتوبة في الجزء الرابع، وقائمة الاستبعاد ملزمة، وكل فكرة جديدة تذهب لـ backlog كـ ADR مرشحة لا تُنفذ فوراً. *طوارئ:* تجميد نوافذ ميزات — إصدار دوري يُغلق حصراً على DoD.

**R-04 — اقتصاد الاستدلال.** مهمة بحث عميقة قد تحرق ما يعادل اشتراك في دقائق. *مؤشر مبكر:* تقرير `ledger` لكل 10 مهام — متوسط كلفة/مهمة واتجاهه. *تخفيف:* L0/L1 يبتلعان أكبر قدر من القرارات، budgets افتراضية لكل مهمة، genome يقلل كلفة التكرار (GM-5). *طوارئ:* خفض افتراضيات العمق + توجيه أكثر حدة للاستدلالات نحو السحابة القابلة للتهيئة أو نماذج أصغر، مع شفافية كاملة للمستخدم عبر الواجهة.

**R-05 — جودة الاسترجاع.** RRF قد لا يكفي على ذكريات فعلية مشوشة. *مؤشر مبكر:* GM-5 يفشل عتبة التحسن، أو استرجاع يدوي مرهق أثناء الاستخدام الفعلي. *تخفيف:* مجموعة eval استرجاع حقيقية من البداية (المرحلة 1 تخزن ذكريات تُبنى منها الحزمة)، معايرة أوزان من eval لا من الذوق. *طوارئ:* فتح باب rerank بشرطيه (ADR-013) — كلاهما قياسي، أو إثراء meta rank (علاقات، مشاريع).

**R-06 — تجاوز مهارة ذاتية.** أخطر مخاطر المشروع بنيوياً. *مؤشر مبكر:* أي `SandboxViolation` — **الحدث الأول يستوقف promotion تلقائياً** ويستدعي مراجعة. *تخفيف:* sandbox درجة 1 إجباري لكل self-created، 3 اختبارات بإيصالات، `skill.create` للـ L3 حصراً، وpolicies منع شبكة افتراضية. *طوارئ:* قلب `trust_origin='self_created'` إلى معطل كامل بأمر واحد (`vara skills quarantine`) مع استمرار builtin.

**R-07 — انسداد SQLite.** *مؤشر مبكر:* p95 كتابة في PersistenceActor > 50ms في اختبارات الحمل، أو تنمو الـ WAL باستمرار. *تخفيف:* دفعات قصيرة (ADR-009)، فهارس §Schema، تنظيف mailbox/access مؤجل، wal_autocheckpoint. *طوارئ:* أرشفة ذكريات قديمة إلى جدول بارد + إن لزم: تجزئة عمودية للجداول الباردة إلى DB ثانٍ — تظل SQLite، لا Postgres.

**R-08 — WebKitGTK.** *مؤشر مبكر:* أول smoke test واجهة على Fedora/Ubuntu — لو الرسومات المتحركة (org tree) تكسر مبكراً. *تخفيف:* الواجهة تُبنى CLI-first (المراحل 0-2 كاملة بلا GUI أصلاً)، فالواجهة تصل ناضجة فوق أساس مستقر. *طوارئ:* توثيق Windows/macOS كأولوية العرض وdaemon+browser client على Linux (نفس daemon مصادَق) حتى يستقر.

**R-09 — ابتلاع التمايز.** Muse/Dots قد يضيفون "منظمات ديناميكية". *مؤشر مبكر:* مراجعة ربع سنوية للإعلانات الكبرى. *تخفيف:* الخندق ليس الميزة الوحيدة بل **المجموعة**: local-first + ownership + portability (هم بنيوياً لا يقدرون عليها) + التركيز على جبهة البحث الجاهزة للتحقق. *طوارئ:* تعميق الندرة الوحيدة المتبقية (الملكية) — vpkg، أدوات نقل، وعديم الحساب = ميزة بيع، لا نقطة ضعف.

**R-10 — sqlite-vec pre-v1.** *مؤشر مبكر:* فشل `fs verify`/استرجاع لأسباب امتداد، أو تغيير breaking في إصدار جديد. *تخفيف:* كله خلف `MemoryStore` trait + جدول vector اختياري معطل قابل للإزالة، GM استرجاع يكشف أي تدهور. *طوارئ:* التبديل إلى Qdrant Edge خلف نفس الـ trait — خطة اليوم (X-10) لا قرار طوارئ آني.

**R-11 — فقدان الزخم.** مشروع مفتوح بلا ضغط خارجي. *مؤشر مبكر:* مرور أسبوعين بلا إغلاق بند DoD واحد. *تخفيف:* المراحل مقسمة بنداً بندياً صغيراً قابلاً للإنجاز في جلسة، وكل سيناريو قبول = "فوز ملموس" قابل للعرض، والـ eval يعطي منحنى تقدم محفوظ. *طوارئ:* تقليص إلى "نواة أسبوع" (PersistenceActor + Gateway + GM-1) — أصغر شيء يحيي المشروع ويعيد الوضوح.

**R-12 — تسريبات الإلغاء.** *مؤشر مبكر:* عداد عمليات الأبناء/الملفات المؤقتة بعد 100 إلغاء اختباري ≠ نقطة الصفر. *تخفيف:* عقد الأداة (on_abort إجباري) + "janitor" دوري (idle) يطابق العمليات الحية مع tool_calls الحية ويقتل الأيتام مسجلاً. *طوارئ:* إيقاف الأدوات الخارجية كاملة والبقاء على builtin حتى الإصلاح — المهمات تتدهور لوضع مقيد موثق، لا تُلغى صمتاً.

**R-13 — backpressure الأحداث.** *مؤشر مبكر:* أحداث `PersistenceBackpressure`/`EmbeddingLag` بتردد متزايد. *تخفيف:* قنوات bounded + أولويات + سياسة إبطاء المرسل (لا إفلات)، والمشتركون البطيء (UI) يقرؤون من DB بالـ seq عند تخلّفهم. *طوارئ:* وضع حمل منخفض تلقائي: تجميد بث الاشتراكات غير الحيوية، والبقاء على كتابة/قراءة DB مباشرة.

**R-14 — هلوسة التقارير المبكرة.** أول انطباع يصنع أو يقتل. *مؤشر مبكر:* نسبة الادعاءات بلا مصدر في مخرجات GM-1 (فحص قابل للأتمتة). *تخفيف:* مهارة `research-basic` تلزم اقتباس كل ادعاء بصيغة مرجعية، والوضوح في الواجهة: "أداة بحث، تتحقق من المصادر، لا حقيقة مطلقة"، وكل تقرير يحمل قائمة الثقة/الفجوات. *طوارئ:* رفع حد أقصى للأدعاءات غير المستندة = صفر + إعادة توجيه للاستدلالات الثقيلة L3 للتحقق قبل النشر.

**R-15 — تضخم الحالة.** كيان يعمل سنوات يكبر بلا معنى إن لم يُعتنى به. *مؤشر مبكر:* حجم state.db + objects شهرياً؛ نمو بلا نمو استخدام = إنذار. *تخفيف:* مهام تنظيف مجدولة (mailbox مسلّم > 30 يوم، memory_access، GC artifacts بفترة السماح)، وأرشفة ذكريات منخفضة الوصول. *طوارئ:* أداة `vara db compact` + استرجاع من export — لا يعاد تصميم شيء تحت ضغط.

# القواعد العشر التي لا تُكسر

المستخلص التنفيذي من الـ 22 ADR — تُطبع وتعلق فوق الشاشة. لكل قاعدة آلية إلزام معلنة:

| # | القاعدة | من يُلزمها |
|---|---|---|
| 1 | **كل الكتابة على SQLite عبر Persistence Actor وحده** — لا استثناء لأحد أبداً | CI: يمنع Connection كتابة خارج `vara-state::persistence` |
| 2 | **لا رسالة وكيل تعيش في الذاكرة وحدها** — durable-first إلى `agent_mailbox` قبل التسليم | مراجعة كود + اختبار GM-3 |
| 3 | **لا استدعاء نموذج خارج Gateway، ولا استدعاء بلا صف Ledger** | CI grep + اختبار A0-T1 |
| 4 | **L1 لا يمسك أدوات — حتماً** | A0-T3 + نظام أنواع الـ Gateway |
| 5 | **لا مهارة self-created دون sandbox + 3 اختبارات ناجحة موثقة** | خط إنتاج المهارة يرفض بنيوياً + A3-T1 |
| 6 | **events و ledger إلحاقيّان** — UPDATE/DELETE يرفضهما trigger | Trigger في الـ Schema + اختبار CI |
| 7 | **كل أداة غير idempotent تُعلَّم irreversible وتشترط ask** | ToolRegistry يرفض التسجيل بلا تصنيف |
| 8 | **الـ CI يعمل بلا شبكة** — MockProvider فقط؛ الاستدلال الحقيقي مستثنى صراحة | إعدادات CI معزولة + فحص |
| 9 | **الواجهة لا تحتفظ بحالة حقيقة** — projection من events حصراً | مراجعة كود + اختبار A3-T6 |
| 10 | **لا فشل صامت**: كل فشل ينتج حدثاً مسماً وصف audit عند الأمان | مراجعة: كل `unwrap/expect` في مسار إنتاج مبرر، وإلا حدث + معالجة |

# مصفوفة التماسك النهائية

الحلقة الكاملة: **ثغرة → قرار → وحدة → مرحلة → إثبات**. هذا الجدول هو "بصمة الإغلاق" — أي صف لا يمكن تتبعه من طرفه لطرفه الآخر = ثغرة في الوثيقة نفسها.

| الثغرة | القرار | وحدة الكود | مرحلة | إثبات الإغلاق |
|---|---|---|---|---|
| G-01 كاتب SQLite | ADR-009 | vara-state::persistence | 0 | اختبار 50×1000 + A1-T2 |
| G-02 Mailbox | ADR-010 | vara-core | 1 | GM-3 + A1-T2 |
| G-03 إلغاء نظيف | ADR-010 | vara-tools | 1 | A1-T3 |
| G-04 Replay | ADR-011 | vara-state | 1 | GM-3 + trigger test |
| G-05 L1 tools | ADR-012 | vara-gateway | 0 | A0-T3 |
| G-06 Rerank/RAM | ADR-013 | vara-memory | 2 | A2-T3 |
| G-07 Gateway/اقتصاد | ADR-014 | vara-gateway | 0 | A0-T1 + GM-4 |
| G-08 WASM مبكر | ADR-015 | vara-sandbox | 3 | A3-T1 |
| G-09 أسرار headless | ADR-016 | vara-policy | 3 | A3-T4 |
| G-10 Compiler | ADR-017 | vara-core::context | 1 | GM-1/GM-2 manifests |
| G-11 Model Manager | ADR-018 | vara-gateway::modelmgr | 0 | A0-T2 |
| G-12 Daemon auth | ADR-019 | vara-cli::daemon | 3 | A3-T5 |
| G-13 انحدار صامت | ADR-020 | vara-eval | 0+ | CI Gate |

| G-15 CAS عقد | ADR-022 | vara-state::objects | 1 | A1-T1 |

**قراءة النتيجة:** 15 ثغرة ← 14 قراراً (ADR-010 تغلق اثنتين) ← 12 وحدة ← 4 مراحل ← 20 إثباتاً (A0..A3 + GM-1..6، منها GM-6 حاكم). الحلقة مغلقة من كل أطرافها — **وGM-6 يقيس أن الحلقة نفسها تستحق الحياة قبل أن تُبنى**.

# المسرد المختصر

| المصطلح | المعنى في سياق Vara |
|---|---|
| **Actor** | وحدة تنفيذ منطقية (Tokio task) لها mailbox دائم وحالة وميزانية — ليست عملية نظام |
| **Persistence Actor** | الكاتب الوحيد لـ SQLite، يجمع الكتابات دفعات معاملات قصيرة |
| **Mailbox دائم** | صندوق بريد الوكيل في SQLite؛ يُكتب فيه قبل التسليم، ينجو من الانهيار |
| **Checkpoint دلالي** | لقطة اتساق عند حدث ذي معنى (انتقال حالة/إتمام أداة) — لا مؤقتات أعمى |
| **RRF** | Reciprocal Rank Fusion: دمج نتائج البحث النصي والدلالي والميتاداتا بلا نموذج |
| **Golden Mission (GM)** | مهمة قياسية تُشغل آلياً لحماية سلوك الكيان من الانحدار |
| **Context Compiler** | المصنع الحصري لمحتوى الـ prompt، بميزانية tokens وشفافية مصادر |
| **Budget Middleware** | بوابة حجز/تسوية في الـ Gateway تفرض ميزانيات المهام والوكلاء |
| **Cost Ledger** | سجل إلحاقي لكل استدعاء: من/لماذا/كم — أساس الاقتصاد الداخلي |
| **CAS** | Content-Addressed Storage: هوية الملف = sha256، والتكرار بنيوياً مستحيل |
| **vpkg** | حزمة نقل الكيان (export/import) — تستثني الأسرار والنماذج |
| **Mission Genome** | هيكل فريق/مهارات مهمة ناجحة محفوظ لإعادة الاستخدام |
| **Supervision** | شجرة إشراف: إعادة تشغيل محدودة ثم قرار معلن (escalate/downgrade/terminate) |
| **L0..L3** | طبقات الذكاء: كود → نموذج صغير بلا أدوات → عام → ثقيل |

# كيف تتطور هذه الوثيقة

1. **قرار جديد** → `ADR-023` وما بعدها بنفس القالب حرفياً (السياق/البدائل/القرار/العواقب/قاعدة الفحص) — في `docs/adr/` مع إضافة سطر في خريطة الثغرات إن كانت تغلق واحدة.
2. **تغيير قرار قائم** → ADR جديدة `supersedes: ADR-0NN` — القديم لا يُحذف ولا يُعدَّل؛ تاريخه هو جزء من ذاكرة المشروع.
3. **ثغرة جديدة** تُكتشف أثناء البناء → تُرقّم `G-16+` وتدخل الخريطة فوراً — القاعدة: **لا إصلاح بلا رقم وثيقة**، حتى يبقى سجل التعلم مرئياً.
4. **بداية كل مرحلة MVP** → مراجعة سجل المخاطر + تأكيد أن كل قواعد العشر ما زالت مُلزمة فعلياً (فحص CI يعرض تقريرها).

> **السطر الأخير:** وثيقة الرؤية قالت *ماذا*، ووثيقة الـ Stack قالت *بماذا*. هذه الوثيقة قالت *كيف تحكم على الصواب أثناء البناء*. المشروع الآن جاهز للبناء — يبدأ من بند أول في Definition of Done للمرحلة 0، ولا يُتقدم خطوة بلا إثبات يخلفه.
